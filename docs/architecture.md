# Architecture

Cutroom has one local server and a React workspace. The Electron application is a contained desktop host for that same interface. Startup and shutdown share one lifetime, including a backend that has not finished opening. Linux installation stores immutable app versions under the user data directory and switches a launcher symlink after the copy completes. Project data stays outside those app folders.

The desktop's owned backend also stops when its parent IPC channel closes, including after a forced desktop quit. An existing server that the desktop connects to keeps its independent lifetime.

On Linux the desktop starts Chromium with `--disable-gpu-memory-buffer-video-frames`. Without it, Chromium copies software-decoded video into native GPU buffers, and on an NVIDIA GPU under Wayland those draw every BT.709 video with the BT.601 matrix, up to 22/255 off. Ordinary texture uploads keep the video's tagged colours, and 1080p playback measured the same frame pacing with slightly less CPU. CI has no GPU, so `bun scripts/desktop-colour.ts` checks the desktop viewer locally: it opens a private Cutroom window, plays tagged BT.709 and BT.601 bars, and fails when a paused or playing picture moves more than 6/255 from Chromium's colour-managed reference. Include it in the Electron upgrade checklist. It also checks that the HTML-in-Canvas methods used by adjustment layers are available.

## Project ownership

Projects remain ordinary HyperFrames folders. The application registry records their paths, while `cutroom.json` stores annotations and original word-timed transcripts. Review status lives in `.cutroom/review.json`, outside project history. `src/shared/review.ts` defines the one transition table that the UI routes, MCP tools, and agent turn lifecycle all pass through, and `src/server/projects/review.ts` runs every review change, plus the note deletes, edits, undo, and redo that could race one, in a single queue per project. One reconcile step there derives status from the live notes and review.json and saves it, before every read and around every history change. Source media is never rewritten by script cuts.

Cutroom keeps one history per project. The owner shares a history identity across tabs. Each MCP connection and native agent conversation has its own identity for the lifetime of the server. Display names and review entry IDs stay independent of that identity. Cutroom settles observed writes and snapshots the caller's next step. The editor addresses each Undo or Redo request to the entry it showed. Each write that commits an entry, except an import, returns the entry's ID in `x-cutroom-history-entry`, so the tab that made it can undo it before it reads the history again. Imports and outside changes are recorded but skipped by ordinary Undo. Studio's step and exact-edit routes use the same selection and authorization.

Exact replay uses recorded file versions. If a composition has changed since the target edit, Cutroom compares each clip's authored attributes, inner content, and presence against the before and after states. It merges independent changes and validates timing, links, transitions, and newly restored media references. Project settings merge by field, with markers and notes matched by ID. Planning runs after a checkpoint, outside the engine queue. The engine checks that the history head and consulted hashes still match before it writes the planned changes. The search for an **Undo both** group caches each file's inverse by the versions it read, and stops after a fixed number of computed inverses rather than a time limit, so a busy machine finds the same group. The confirmation plans exactly the confirmed group once. The engine records each inverse as a separate entry. Skipped owner edits are saved in `.cutroom/history-skips.json`, which drops entries the log no longer holds. On reopen, the engine also removes temporary files left beside an interrupted replay's paths. On reopen, the engine rolls back files still matching an interrupted replay, keeps outside writes, and logs a warning for files it could not recover. The editor shows the step at the keypress from the timelines it remembers around the edit, and receives the confirmed timeline in the replay response. When other editors changed the timeline since, it shows the step only if their changes left the edit's clips, markers and settings alone and lie before the first clip the edit moved; otherwise it waits for the engine. Like an unsaved edit, the shown step is reapplied over any read that lands before its answer, so it never waits behind a reread of an agent's change.

`src/server/projects/store.ts` owns the project registry, serialized Cutroom mutations, and one `ProjectHistory` per folder from `src/server/history/`. Cutroom owns the engine source, adapted from HyperFrames 0.9.26. The native editor, transcript service, and MCP tools use that same history, with Studio routes reaching it through the adapter. Existing project IDs, logs, and blobs open in place. Histories live in Cutroom's data folder and are never deleted on a timer. Cutroom's engine disables HyperFrames' 14-day pruning because a moved folder or a deleted `.hyperframes/history-id` can make a project look gone. Source writes require the exact content version they read. Metadata writes also refuse concurrent replacement. Shutdown rejects new edits and drains admitted mutations before closing history. The notebook reads review items and a transcript revision; full words load when Script is opened.

Home lists registered projects, most recently edited first, and shows the first-run screen only while the registry is empty. Renaming (`PATCH /projects/:id`) changes only the registry's display name, so the folder, history, watchers and agent working directories keep their path and agents keep the project ID. Removing (`DELETE /projects/:id`) drops only the registry entry, after admitted edits finish, and closes the project's history. The folder and its history stay on disk, so importing the folder again reattaches the history under a new project ID; earlier agent conversations stay with the old ID. The route refuses with 409 while the project exports or an agent is working in it, and refuses any request carrying an agent credential, so MCP has no remove tool. `project_rename` is exposed because a name is display-only and reversible, and an agent naming the project it created or was asked to label saves the owner a step; an in-app agent can only rename the project its turn runs in. Duplicating (`POST /projects/:id/duplicate`) copies the project into a new folder beside the original, so it stays on the same disk, named "<name> copy" (then "copy 2" and on, never a name on the list or in a running duplicate). It is built in a hidden staging folder, `.cutroom-duplicate-<pid>-<uuid>`, created with mode 700 and written through its open handle, holding a marker that records the host, boot id and process. Under the source's mutation lock, after a history checkpoint, Cutroom walks the project without following a link (each folder is opened with `O_NOFOLLOW` and read through that handle) and copies every file up to 1 MiB, cloning where it can. Larger files copy after the lock is released, on the same serialized copy queue as media import, so edits never wait on them: each is cloned (`COPYFILE_FICLONE_FORCE`), or else byte-copied after one free-space check for all of them, with progress and Cancel. A duplicate never hard-links, so a tool that rewrites a file in place in the copy cannot change the original. Every source is opened without following a link and must still match the size, inode and mtime the walk saw; `.cutroom/view.json` and `review.json`, which are replaced outside the lock, are copied as they are when copied. A name that is not valid UTF-8 is refused by name. A link is kept only when it is relative and its real path, through every link on the way, stays inside the project. The copy leaves behind what belongs to the original: `.hyperframes/` (the history id, render records and preview state), `.cutroom/review-ledger.json`, `review.v1.json` and `history-skips.json` (they point at history entries the copy lacks), the ledger rows older builds kept in `review.json`, `.cutroom/cache` (its keys name the source file's inode and times, which a copy never matches), `.cutroom/renders`, `renders.json`, `trash/`, `.thumbnails/` and atomic-write temporaries. With no history id, the copy's first open starts fresh history with the copy as its baseline. Once complete, the staging folder takes an empty folder Cutroom just made under the final `<slug>-<id8>` name, so it never replaces anything else, and only then is registered. If registering fails, the folder moves back to its staging name and is removed, so a crash or failure never leaves a half-copy on the list. At startup Cutroom removes staging folders in the projects folder and beside registered projects only when the folder and marker are real files owned by this account, the marker is at least ten minutes old and from this host, and its process is gone or its boot has ended. Cancel and failure remove the staging folder. Home polls the job (`GET /duplicates/:job`) and shows the copy's tile with progress and Cancel until it is listed; an in-app agent sees only its own project's jobs. Duplicating is refused with 409 while the project exports or another agent works in it. `project_duplicate` is exposed because it only adds a project and never changes or removes the original, which makes it the safe way for an agent to try a risky change; it always asks, like project creation, because it writes outside the project. Cancel removes files, so only the owner can cancel. The registry is written to a temporary file and renamed over `projects.json`. Last-edited dates use the newest mtime of `index.html`, `cutroom.json`, the project's other timelines (compositions at its root), and their linked authoring sources, including nested sub-compositions, styles, scripts, JSON and SVG. The source graph follows local references with the existing source-write boundary, including HyperFrames' sibling-first/project-root fallback. It lists only the project root, to find its timelines, and never follows media files or reads private app state. The list reads those dates on demand. Each project then loads lazily once its tile has been on screen: `GET /projects/:id/summary` reads the root composition's size and length through the timeline's own parser, and the poster is the upstream thumbnail route at full size, one second in. That route renders one frame at a time and caches it under the project's `.thumbnails/` by content, so a second visit reads files. A tile that leaves cancels its request, so an unfinished render never holds a connection the editor needs. Listing projects, rendering posters and resolving files do not start file watchers. The editor project-events subscription starts one shared preview watcher per open project and releases it when the last subscriber leaves. The media/review watcher belongs to that same open connection. Closed projects recompute signatures on demand because no watcher can invalidate a cached signature.

External changes are watched and sent to the editor through server-sent events. The editor preserves its own file-write receipts, selection, playhead, and conflict handling.

Dot folders such as `.cutroom/` hold app state, including review captures and renders. They are left out of the project file list that Media, Assets, and the code tree read, and their changes do not refresh Media.

`projectWritePath` is the server boundary for user-directed source writes. It allows HyperFrames' authored text types and the editor's `.htm` alias, refuses hidden segments and instruction/tooling configuration, and checks both the requested path and the canonical symlink target. Source saves, timeline/script mutations, and the embedded editor use it for agents and owners, independent of approval. Media management keeps its asset types but cannot target protected files. Embedded renames are refused when the upstream reference writer's project-wide text scan could touch protected content. That scan reads hidden folders too, so it refuses every project the editor has opened (`.cutroom/cache` holds JSON) and every imported HyperFrames project (they ship `CLAUDE.md` and `AGENTS.md`). A Media rename reads only sources `projectWritePath` allows. `mediaReferences.ts` scans HTML attributes, CSS URLs, and script/JSON strings and resolves each path against its declaring file before matching. Existing sibling paths take precedence over legacy project-root references. Changed sources use the normal source writer with expected versions, inside the file move's history window. Protected files are never in the writer's reach. A successful rename moves persisted source marks through `moveSourceMarks`; history moves them back or forward with the corresponding file move. Media refreshes close a source whose path disappeared, and Insert/Overwrite verify it still exists before placement. Range-export preparation skips `trash/` and `.cutroom/`, while history continues tracking the trash. The editor rewrites `.cutroom/` while an export runs (media-cache scratch folders are renamed into place, state files are replaced), and a copy that walked it failed whenever an entry vanished mid-walk. History validates the files an undo or redo would change; its fixed app sidecars remain available, without allowing links from them to native settings. App-owned hidden sidecars use `projectStatePath` to refuse redirected write targets; public `cutroom.json` follows the source-write boundary too. This prevents a metadata symlink from redirecting an annotation or review write onto native permissions.

### Timelines

A timeline is a root-level HTML composition, decided by one rule, `isTimelinePath` in `shared/sourcePaths.ts`; `index.html` is the main one. Per-timeline state was already keyed by composition path: `cutroom.json` `timelines[path]`, transcripts by `sourceFile`, annotations by `compositionPath`, `.cutroom/view.json` `timelines[path]`, the review ledger by composition and clip. `src/server/projects/timelines.ts` duplicates one inside one store mutation, so one history entry holds the new file, any copied captions files and the `cutroom.json` change. The copy's transcripts take new ids, because the editor and MCP address a transcript by id alone; the copy's `data-cutroom-transcript` and `data-cutroom-anchor` attributes and its captions hosts' `data-composition-src` are rewritten in place, every other byte kept. Clip ids stay the same in both files. The clip-id ledger is project-wide and generates new ids around every id ever used, and everything else per clip is keyed by composition as well. View settings are copied after the entry, outside history. A file at the root resolves media and scenes exactly as `index.html` does, so nothing else is rewritten.

The editor opens one timeline and reads only that one. `GET /projects/:id/timeline-open` names the timeline the project reopens on, saved in `view.json` as `open` whenever a timeline is shown; the editor waits for it before it reads a timeline or mounts the viewer. Lint runs on its own worker thread (`src/server/hyperframes/lint.ts`): at 1,000 clips HyperFrames takes about 400 ms to lint a timeline, which on the request thread held every other request, such as an Undo pressed right after an agent's edit. Lint drops HyperFrames' `multiple_root_compositions`, since Cutroom always names the composition it previews or renders, and lints each timeline as an entry, never as a scene. The editor names its open timeline when it asks for lint: that one gets HyperFrames' full project lint from it as the entry, which probes its media and checks its scenes, and every other timeline gets a lint of its own file, kept by content hash until its bytes change. A request that names no timeline, as `project_lint` and the legacy editor send, lints every timeline in full. Switching timelines lints again after the same 400 ms pause as a save, so the switch reads its timeline first. With six 1,000-clip timelines, a save's lint takes about 380 ms instead of 1.6 s on main. A duplicate's history entry has its own category, `timeline`: undoing it is held back only by later edits to the files it made or edits that mount the copy, never by edits in other timelines. HyperFrames follows mounts from `index.html` only, so file events complete its answer: a change to a scene also names every other timeline that plays it, and a change to a timeline nothing mounts names only that timeline. An edit to one timeline never reloads another's preview, and an edit to a shared scene reloads every timeline that shows it. Undo and redo replies name the timelines the step changed, reading the `timelines` settings in both versions of `cutroom.json` when a marker, track or In/Out edit changed nothing else, so the editor can say where a step landed. Undoing a duplicate also drops its `view.json` settings. A rename moves the file and rekeys `cutroom.json` (settings, transcripts, annotations) in one `timeline` entry, rewriting references in any file that mounts it the way a media rename does. State outside history moves after it, in the review queue: `review.json`'s copies of sent notes, so they do not read as changed and get withdrawn, the review ledger's targets, and `view.json`'s settings and `open`. When undo or redo moves a timeline file, found as one path removed and another created with the same content, the same state moves back. A new timeline is `timelinePage` from the store, the starter page without clips, at the size and rate of `index.html`. Timeline names follow the project-name character rules and stay within 200 bytes, so a copy number and `.html` keep the file name under 255.

## Editor integration

See the [design system](design.md) for Cutroom's UI tokens and shared controls.

The public `@hyperframes/studio` application supplies the timeline, canvas editing, preview, inspector, and source editor. Cutroom supplies the surrounding workspace, review tools, agent panel, and original visual theme.

The shell is a fixed, dark-only layout: Media above one work panel on the left, the editor beside them, and a status bar below. Agent, Review, and Script share the work panel. Their components stay mounted while switching tabs so drafts and native sessions survive navigation. Transcript reads run only while Script is visible. Every colour, type size, space, radius, line weight, layer, duration, and easing is a token in `src/client/tokens.css`, a verbatim copy of the design source that `src/client/styles.css` imports once. Its `@custom-media` breakpoints are expanded at build time by Lightning CSS. `styles.css` only arranges the tokens and maps them onto the names the embedded editor reads. Components contain no colour literals. Motion animates only transform and opacity, nothing loops, and reduced motion collapses movement to short fades through the same tokens.

The viewer zoom, export quality, agent conversation/provider/model and Script footage pickers share `SelectMenu`, extracted from the viewer's anchored popover. Its combobox trigger controls a listbox with arrow, Home/End and type-ahead navigation. Enter or Space selects; Escape returns focus to the trigger without closing an enclosing dialog. Tab dismisses it and continues through the form. Popovers use the same transform/opacity motion and reduced-motion tokens as the viewer menu.

Shell controls read and write `src/client/workspace.ts`, a Cutroom-owned store for editor panel visibility, export state, the open composition's frame rate and size, and the chat panel's agent availability. `CutroomEditor` is the only code that mirrors it onto the upstream dock, so the shell does not depend on the embedded editor's layout internals.

`build/studioPlugin.ts` applies explicit, version-checked changes to the published source. It replaces branded chrome, removes hosted catalog and feedback, disables telemetry, and connects agent handoffs. The source package remains an upstream dependency rather than a copied editor fork.

Keep the HyperFrames packages on the same version. An upgrade must review each source transform, run the editing and preview/export tests, and inspect the workspace in a real browser. A successful build alone is insufficient.

For an upstream upgrade, update all `@hyperframes/*` dependencies and the `hyperframes` CLI together, then update `SUPPORTED_VERSION` in the build plugin. Source transforms fail when an expected upstream section changes. Review that change, adjust the integration, and run `bun run check`, `bun test`, and `bun run test:e2e` before packaging. Public editor improvements then come through the dependency. Features exclusive to the proprietary desktop application require independent implementation.

## Cutroom's own editor

`src/client/edit/` is the editor a project opens in. The embedded HyperFrames editor remains available when New editor is switched off. The default viewer uses the same HyperFrames runtime in an iframe at the composition's size, scaled to fit. `/api/projects/:id/isolated-preview` redirects to a random, server-session capability for that project's preview documents, runtime, GSAP, and assets. That capability cannot serve API routes or another project. The response CSP and iframe sandbox both permit scripts without `allow-same-origin`, so composition code has an opaque origin and cannot access the editor's DOM, storage, or API. Playback, clock updates, dimensions, and seek/paint confirmation cross a message bridge checked against the frame's window. The bridge exposes only preview operations. A local seek, play or pause keeps its requested time and playback state until the iframe acknowledges the latest command; queued runtime state and clock messages cannot restore an earlier position during that gap.

`createTransport` in `transport.ts` is the playhead state machine, and it has two instances: the timeline's, attached to the preview runtime, and the source viewer's, attached to a media element or, for a still, a clock. Whichever the viewer shows is the one the transport bar and keys drive. The source viewer lies over the stage instead of replacing it, so the timeline's preview keeps painting underneath and an edit made from the source still completes its reload handoff. Source marks entered before the initial preference read are retained in source seconds and applied to the source transport immediately. Once that read supplies the media identity, the pending marks enter the existing save queue. A late read cannot replace them with the saved range.

Before a paused preview is promoted, the bridge acquires a decoded `VideoFrame` for every visible video and draws the hold canvases from those frames. Refreshes update those canvases in place. The viewer then requests another paint after making the replacement fully visible. It retains the last confirmed iframe until that acknowledgment. There is only one candidate; a newer edit replaces the pending refresh destination instead of stacking documents. Hit testing, selection geometry and warnings belong to the document the viewer shows. Preparing a candidate does not claim that ownership. Each hold owns its frame until replacement, native playback, or document teardown. Teardown closes decoded frames, clears hold ownership, stops native media, and ignores queued bridge messages without clearing the last painted canvas, which the compositor may still show while retiring the iframe. Missing decoded frames keep the previous picture within the fifteen-second preparation deadline; media readiness alone does not confirm a captured picture. A paused native seek registers a video-frame callback before moving the media clock. Presentations stay observed until a decoded timestamp matches the captured picture; a new video can present its initial picture before the requested one. The effective seek destination is clamped to the source duration before replacing that observation, so a repeated seek at EOF keeps its confirmed final frame. Chromium can finish a seek while still supplying the previous decoded picture, which is rejected and retried within the existing deadline. The check uses frame identity rather than nominal duration, so a picture held through a VFR gap or a longer audio track remains valid. Playing, replacing a source, removing its clip, and tearing down the document cancel pending callbacks. The runtime has a hold of its own: while a video seeks, it shows a still copy and sets the video to `display: none`. That cancels the video's CSS animations, and the runtime's CSS adapter keeps their handles, so its next pause revives each cancelled transition beside the new one and the fades multiply. The bridge keeps a video with a transition laid out but invisible during that hold, so it keeps one animation per edge.

Timed media start without an eager preload hint unless the source sets one or uses autoplay. The preview runtime loads media around the current playhead and releases buffered media with direct source URLs as their clips leave the window. GPU playback also parks the videos it draws on the parent canvas and limits native audio around the playhead. The preview retains clip elements for CSS, hit testing and live edits. When it checks the composition's duration, the CSS and Web Animations adapters share one document animation query.

A live document that reloads itself uses the same iframe slot through preparation and promotion. Its teardown notifies the handoff before the replacement loads. The transport detaches without changing the frame or playback intent, and disposed connections cannot send commands through the iframe's surviving window to its replacement. Play and pause during reload update that intent; only the confirmed replacement attaches and resumes the clock. The stage's `data-handoff` attribute exposes the lifecycle for browser checks.

Isolated documents have a default-deny CSP. Scripts, styles, media, fonts, and fetches can use only that capability's assets, with inline composition scripts/styles and embedded data or blob media permitted. Forms, child frames, objects, and workers are disabled. Asset responses permit the opaque `null` origin; other API reads reject it. The editor document's `frame-src 'self'` also prevents the isolated frame from navigating to an external site. The server rejects `Sec-Fetch-Site: cross-site` requests outside `/api/isolated/`, including Origin-less navigations to old preview documents that would discard those restrictions. Trusted parent loads are same-origin, and native clients without that header retain their existing access. A `Connection-Allowlist` scoped to the same assets blocks additional Chromium network channels, including WebRTC and speculative connections; DNS prefetch is also disabled. Full network confinement requires a Chromium version that supports that header, as bundled in the desktop app. Other engines still enforce the sandbox, CSP, and API Origin boundary but may allow non-fetch network channels. External scripts, fonts, or media must be downloaded into the project before use.

Both isolated preview assets and the producer's source/compiled asset lookups use `projectPath`, shared from `src/server/projects/path.ts` and re-exported by the project store. Each lookup resolves the canonical root and target before serving the canonical file. File and directory symlinks outside that root receive 403; links within it remain usable. Asset MIME types still follow the requested URL. A missing compiled asset can fall back to the source project, while a rejected link cannot.

**Known limitation:** **New editor** is on by default, so projects open with composition isolation. Switching it off restores the old embedded `@hyperframes/studio` editor, which still uses `/api/projects/:id/preview` on Cutroom's own origin. Its canvas tools require direct preview DOM access. That route is deliberately unchanged while the upstream editor awaits removal. Composition scripts in that editor can still read other projects, write through the API, answer pending agent approval prompts, access the parent UI and storage, and contact external sites. The request guard accepts their same-origin requests, so it does not close those attacks. Keep agent-authored compositions in the new editor; the upstream-removal PR must remove this remaining trusted-content path.

`transport.ts` holds the one playhead: an explicit `stopped | playing | shuttle | scrubbing` state, the frame, and the engine's frame rate, length, and in/out range. React renders only state changes; the timecode, playhead, and agent context subscribe to the store and follow the frame without rendering. At 1x the runtime plays its own media and its clock drives the frame, so sound stays in sync. Stopping parks the runtime exactly on the frame its clock reached. At 23.976 and 29.97 the runtime's end time floors one frame short of the engine's exclusive end, so the runtime stopping by itself on the last frame ends playback or loops it. K held with J or L is `jog.ts`: a small reducer over key presses, releases and a 250 ms hold timer that turns them into frame steps, a half-speed shuttle (`slow`, 0.5x) and stops. It counts only keys physically down, tracked from key-down and key-up and cleared when the window loses focus, so the same action from a menu just shuttles or stops. Shuttle speeds and reverse step the runtime one seek per displayed frame, and the [scrub and shuttle sound engine](#scrub-and-shuttle-sound) plays their sound, as it does for dragging the playhead and stepping frames. Seeks made while scrubbing or shuttling are marked as moving, so the viewer may show a [scrub proxy](#scrub-proxies) first; stopping always seeks the exact frame. `timeline.ts` keeps the engine's timeline and undo state for the open composition. Reads, edits, undo, and redo go through one queue, so each starts from the view the previous one left. An edit is applied to the shown view at once with the shared `apply`, so the next key or click already sees it, and stays pending until the server answers. Each read shows the server's timeline with the pending edits applied on top, and a refused edit is taken back while the header toast shows the engine's reason. An edit's commands are built once, from the shown view when the key is pressed, and never rebuilt: a rebuild against newer server state could pick other clips than the ones the user saw. The queue writes an id for every piece the commands cut into their `ids` lists, so the shown piece and the server's piece share an id (the engine never hands out an id twice). A trim, razor or move also snapshots every clip it changes, including linked partners and ripple followers, since a trim or razor cuts at absolute frames and a drag moves a clip to the place the user saw. An overwrite move also snapshots each destination range and the clips occupying it, including empty ranges and linked partners' ranges. An agent moving or inserting a clip into that space changes the snapshot and refuses the edit. A mouse gesture keeps its starting timeline from the press and passes it with its frozen commands on release. The held preview and the queue check the snapshots before replaying the commands, on release, and again before sending them, including after a stale-revision retry. A changed clip refuses the gesture; unrelated edits stay underneath its preview. Export starts through this same queue after earlier edits have settled, and a refused edit is reported instead of rendering the saved version. A stale revision (409) means someone else edited first; the step reads the server, checks those clips again, and sends the same commands. If the engine refuses them after that, the clips changed under the edit, and the header says so; a refusal on the first send keeps the engine's reason. When a step fails, it takes back the queued edits that name a piece the failed edit would have made (the editor chose those ids, so the set is exact), removes those pieces from the selection, and reads the server before the queue moves on.

Ripple edits use the existing header toast with Undo after the server accepts them. Whole-clip overwrites from drops, moves and paste use the same toast and history guard, naming the replaced clips once. Inserted media and pastes also name a clip they shortened as partly replaced: either side that survives a cut keeps the clip's id, so a shorter clip lost material. A moved clip's partial overwrite and trims stay silent. A ripple is reported when it changes a track other than the explicitly targeted tracks, including linked sound, or deletes any clip. Same-track trims and their followers stay silent. Q/W, ripple delete, Paste Insert and insert drops share this rule. The message counts the command's time interval, affected tracks and deleted clips, rather than relying on project duration. The toast sends the exact committed history entry ID. The server refuses a stale or conflicting action.

Confirmed timeline reads also compare the previous projection to identify outside edits. The server reads the projection and attribution together under the review queue, so a response cannot pair older clips with newer edit rows. Local command receipts and history steps establish their own baseline and stay silent. Human-attributed clips are excluded from notices, including owner source saves observed through the file watcher. New agent attribution retains the native agent or MCP client name in `agentName`; old rows without a name use "Agent"; unattributed disk changes use "Outside edit". HTTP MCP sessions retain the initialization client name and expire through `server.close()` after 30 minutes without a request. Each request refreshes expiry; in-flight requests suspend it until completion, so a long-running agent tool cannot expire mid-call. Thirty minutes allows long reasoning and shell-work gaps between calls while bounding disconnected-client retention. Explicit deletion and server shutdown cancel the expiry timers and close sessions immediately. The bridge carries that display name separately from the authorization token. Distinct changed clips coalesce after 700 ms of quiet, with a two-second limit during a continuous burst. These notices use a polite status and never move focus. The latest outside notice waits behind foreground feedback in the existing single header slot, preserving refusals, errors and ripple Undo. Its hold starts when it becomes visible; a pending notice cannot reset the foreground toast's hold. A toast with an action (Undo, Redo, Ask agent) keeps the slot until it is used, dismissed or expires: a plain notice that arrives meanwhile waits behind it and then gets its own hold, while a refusal or error answers a press and shows at once. A notice covered after half its hold has had its turn and does not return once the covering toast is gone; one covered sooner comes back for a full hold. Closing the project clears both kinds of notice. Comparisons run on changed revisions, with no playback subscription.

Element clips carry an optional `textPreview` with the first authored line from the existing parse5 tree walk. Entities, nested inline text, line breaks and block boundaries are resolved during that parse; scripts, styles and inert templates are excluded. Timeline labels render this preview beneath the name with the same colour and 10 px type. It fits the 28 px minimum track height, ellipsizes, follows the clip while scrolling, and uses the existing 28 px label mount threshold. Source edits refresh it through the normal timeline read.

Other DOM changes remain significant.

Title snapshots use the existing `readTitle` validation and declared-font check, then carry the actual saved/compiled attribute strings and decoded text nodes, including line breaks and their compiled identities. Scaled rasterization differed across font/motion and plate edits despite identical DOM, computed styles and animation times, including in a fresh/fresh diagnostic. `data-preview-timing-ready` appears only after the viewer has received approval for the live document, independently of its first painted picture. The viewer handoff has one state machine: showing the confirmed picture, checking a live update while retaining it, loading one candidate, promoting that candidate while waiting for its first visible paint, or reporting a failure before returning to the confirmed picture. A reload warms the candidate over the confirmed iframe at 0.1% opacity and seeks it to the latest frame. Coalescing, a superseded candidate or its deadline can change which preparing document is current. The confirmed picture remains until a replacement has painted; iframe identity is not a guarantee per saved edit. Stale async results cannot confirm or fail a newer candidate. Removing the confirmed iframe in the same React commit that reveals its replacement can expose a single blank frame.

Filmstrips and waveforms are drawn by `bodies.ts` on one canvas that lies over the clips, under the selection outlines and names. ## Footage pipeline

**GPU footage playback** is on by default. Settings preserves a user's choice in `cutroom.footagePipeline` in local storage. Cutroom's pipeline draws eligible video beneath the same isolated HyperFrames preview, on the same clock. The preview keeps GPU-drawn clips available for picture selection and snapping, and decodes the source edges it needs while a trim is in progress. The GPU canvas sizes its backing store from viewer resize notifications. HyperFrames draws titles, graphics, and footage that needs native playback. It also draws the preview when WebGL2 is unavailable. See the [desktop measurements](performance.md#desktop-playback).

`GET /api/cutroom/projects/:id/pipeline` classifies the entry composition with `planPreviewPipeline` (`src/server/hyperframes/pipelinePlan.ts`). The classifier shares the direct export's placement rules for muted video, `object-fit`, Position, Scale, Rotation, whole-pixel Crop, Opacity and colour-only grades. A video can also have HyperFrames' standard `clip` class if the stylesheets leave its picture to the compositor. HyperFrames draws titles, captions and sub-compositions in the isolated preview on the same clock. The entry can load the pinned GSAP bytes from `gsap.min.js` or `assets/vendor/gsap.min.js` and register an empty paused timeline. Saving that library triggers a new plan.

The timeline's existing media probe supplies SDR colour tags to the footage pipeline alongside its plan. The decoder uses them when the tags live only in the bitstream, with the container's tags and Chromium's size-based guess as fallbacks. A BT.709 matrix is enough to infer missing BT.709 primaries for both preview and export. An explicit primary tag still takes precedence.

A video stays in HyperFrames if it has its own sound, starts or ends between frames, uses unsupported styling or effects, or is HDR or has alpha in the media probe. The editor logs the reason for each native clip, including when all clips need HyperFrames. A script that can change the footage, a stylesheet that changes the page or footage layout outside the rules, cross-layer blend or backdrop effects, authored stacking the planner cannot prove, or a non-solid page background can keep the whole entry on HyperFrames. An unsupported file that has an [editing proxy](#editing-proxies) uses that proxy in the pipeline when it is ready. HyperFrames can draw from its pieces during preparation. The pipeline limits the decoded playback track to 2,073,600 pixels per frame. Codecs that use editing proxies, such as HEVC, ProRes and DNxHR, can play through a finished proxy that fits this limit even if the source was 4K. The MP4 track supplies the dimensions the pipeline checks before it opens a decoder.

The pipeline paints under the HTML preview. If a title, scene, image or native video lies below drawable footage, HyperFrames composites that overlap. The pipeline resumes on the first safe frame, even inside the same video clip, and playback lookahead can prepare that frame. The plan names clips, but the client checks stacking and draws from its current timeline view so trims, lifts, ripples and undo can reach the picture before the next server plan. A new razor piece can use its neighbour's fit until the plan names it. An unknown video goes to HyperFrames at the affected frames.

Each source file has two WebCodecs decoders (`src/client/pipeline/decoder.ts`) that share a sample index and compressed byte cache, fed from a small demuxer (`mp4.ts`: H.264 and HEVC in MP4 and MOV, a phone's quarter-turn rotation, an edit list of one entry, composition offsets read as signed in either `ctts` version as FFmpeg reads them, since DaVinci Resolve writes negative ones in version 0; fragmented files, an edit list that delays or rearranges frames, and a track matrix that mirrors or scales the picture are refused, and every count, offset and size is checked against the bytes that hold it and the file, with a 64 MB movie header, two million samples and 64 MB per sample as hard limits, so a crafted file fails before it allocates) over byte ranges of `GET /api/cutroom/projects/:id/media/source?path=...`, in 1 MiB blocks. That route serves only MP4, M4V and MOV files outside hidden folders, after the same project boundary check as the other media endpoints, applied to the path asked for and to the file a link resolves to. A file that fails to open is not tried again until the next plan. The pipeline's code loads only once the setting is on. One decoder follows the playhead; the other prepares what comes next, so a cut within one file never waits for a keyframe. Playing, the pipeline decodes the opening twelve frames of every clip that comes into view within the next 45 frames, whether it starts there or a clip above it stops covering it (`appearances` in `layers.ts`). At rest, it decodes the first three frames of the next clip to come into view in each file, within 300 frames, because an edit at the playhead (W, a ripple delete) usually shows that frame next. A frame neither decoder holds or is on its way to goes to the decoder not drawn from last, so the frames just drawn stay for an undo or a jump back, and each decoder keeps the frame it drew last however far the playhead moves. Moving seeks (scrub, shuttle, reverse) decode the [scrub proxy](#scrub-proxies) through a third decoder; every proxy frame is a keyframe at the source's own timestamps. The proxy uses a low-latency decoder and keeps four decoded pictures. At rest, a frame its decoder would have to decode from a keyframe draws the proxy's frame first, marked `data-standin="true"` on the canvas, then the exact frame once it has decoded. A proxy still being made answers 202; the pipeline asks for it again, at most every two seconds, until it exists.

On each display refresh the GPU canvas chooses its frame from the preview's timestamped playback clock. It extrapolates short gaps between clock messages and keeps a stable sample through sub-frame jitter. Seeks, buffering, and a stalled clock reset the sample. HyperFrames continues to run the clock and play the sound.

Playback feeds a decoder straight on into the next GOP and flushes only at the file's end. A draw can take its frame from a running decode. Lookahead queues one missing picture at a time so a draw can go ahead of the rest. A newer lookahead replaces the remaining range, and a frame already submitted gets time to arrive before the decoder is fed more samples. A decode that has fed 32 samples past its frame without it decodes the frame again, from the keyframe before its own: in an open GOP, as DaVinci Resolve renders, the B-frames shown around a keyframe refer to the GOP before it. A frame no keyframe puts out, such as a Resolve B-frame that refers to a picture before the file's first, shows the frame before it, as a paused `<video>` does. Reading on through a file fetches the next 1 MiB block before it is needed. A frame is found by presentation time with the runtime's own media time (`mediaStart` plus clip-local time times rate, plus the runtime's 10 microseconds). Decoding is software with frame threading, like the editor's `<video>`; low-latency decoding kept ahead of 4K60 by only half again, and playback fell to 2 pictures a second. Each decoded frame's colour space is the bitstream's tags when it has them (Chrome's decoder prefers them, for WebCodecs as for `<video>`), else the container's `colr` tags, else Chrome's guess for an untagged stream from `src/shared/videoColour.ts` (#136's rule). The compositor copies an 8-bit 4:2:0 frame's Y, U and V planes out with `copyTo` and converts them in its shader with that space's BT.709 or BT.601 matrix and range, at the picture's own size, each chroma sample covering its 2x2 block, before filtering to the screen, as Chromium draws a `<video>`. Any other layout or matrix, and primaries or a transfer other than BT.709's and SMPTE 170M's, go through the browser's own conversion: Chrome converts other gamuts to the screen's, such as the EBU primaries Android phones tag full-range footage with, which moved blue by 8/255 when drawn as plain matrix arithmetic. That path costs memory: handing a software-decoded `VideoFrame` to `texImage2D` converts it through a canvas whose image cache keeps each converted picture, which held about 500 MB after one drag across the 400-clip timeline. A phone's portrait video is stored turned; the shader reads the stored picture through the track matrix's quarter turn, and object-fit uses the turned size. The scrub proxy is made upright, so each picture turns by its own decoder's rotation. Decoded frames are kept per decoder, nearest where it was last drawn or prefetched, within a shared budget of 128 MiB. A prefetch or a clip's opening decodes only what a third of that budget holds. Twelve 8-bit 1080p pictures fit in that share. The budget can also evict an idle lane's last drawn frame on projects with many sources.

`compositor.ts` draws the layers on one WebGL2 canvas beneath the preview iframes, at the viewer's device pixels: the page colour, then each video with its object-fit, Position, Scale and Rotation about the box's centre, Crop as an inset of the box, opacity, and a dip's brightness. Transition opacity follows Cutroom's transitions stylesheet, computed from the attributes as written (six-decimal seconds), so a frame halfway through a dip falls on the same side as in HyperFrames. A layer under an opaque, untransformed clip that fills the frame is not decoded. Shader sources are constants. Leaving the viewer or turning off the pipeline releases its decoder frames, compositor textures, and grade worker.

While the pipeline is active the viewer tells each preview document `pipeline: true` and the ids of the videos the plan gives it. The bridge then parks those videos, directly in the root composition: the element stays in the DOM that the runtime and the live-update checks compare, but its media properties answer as a ready element at the time the runtime set, advancing while it "plays", and it never loads. A constructed stylesheet, outside the DOM, makes those videos transparent (their ids reach its selector through `CSS.escape`), clears the page, body and root backgrounds, and gives the document the editor's dark colour scheme (its default text colour stays black), since Chromium paints an opaque backdrop behind a frame whose scheme differs from its owner's. Audio stays on HyperFrames' path, but only audio within 2 s behind and 8 s ahead of the playhead stays loaded: the rest is parked and gives its media back, and moving seeks load nothing new. Every other video plays and draws as usual, on top; a razor piece is one of them until the next plan names it. Turning the pipeline off, or a plan that hands a video to HyperFrames, unparks it and seeks the runtime again so it loads. A paused video goes back where the runtime last put it while parked, placed by its frame grid like any paused seek: the runtime would not seek it again within its tolerance, and a grid that arrived while it was parked never placed it. A paused picture that is waiting for frame grids looks again at which videos show natively once they arrive, so a video the pipeline took meanwhile is left alone. When a ripple deletes a video, a retained preview document can still contain that element. Its video stays parked until the document retires, so the old shot cannot cover the new picture.

### Which frame the viewer shows

The viewer shows the frame export writes at every frame, on every path: a source the browser plays, its editing proxy (finished or in pieces), its scrub proxy while dragging, and the footage pipeline. Export reads a constant-rate video on a grid: it snaps each frame's time to `start + k / rate`, the video's start on the media timeline from HyperFrames' probe and FFmpeg's `r_frame_rate`, and shows at each slot the last grid frame starting at or before it. That undoes a container's rounding: OBS writes Matroska (and MP4) on a millisecond clock, so 60 fps frame 1 starts at 17 ms, a third of a millisecond after its slot, and a player seeked to the slot showed frame 0.

`frameGrid` (`src/server/media/frames.ts`) reads that grid once per file version, from the same probes as export, and answers null for variable frame rate, which export reads at the file's own times. The pipeline reads it from `media/frames?path=`, the sandboxed preview from `frames?path=` below its capability. Both seek with `frameSeek` (`src/shared/frames.ts`): a quarter of a frame into the grid frame export picks. That is past the rounding and the millisecond Chromium can show a Matroska frame late, so players that show the frame at or before a seek show it, and short of the middle, past which Chromium's HLS player, which shows the nearest frame in a proxy's later pieces, shows the next.

The bridge puts the rule in every video's `currentTime` setter while the video is paused, and the getter answers the time asked for until the video moves, so the runtime sees its own time. HyperFrames' runtime leaves a paused video where it is when the new time is within 20 ms, so at 50 fps and above a step of one frame never moved it. Before the bridge holds a paused picture, it moves any visible video that is not where `frameSeek` puts the playhead's frame, once per picture.

The editing proxy's packet plan also stores presentation timestamps on the normalized proxy clock. Authored source offsets still use the runtime's media clock. The preview reads the timestamps for the piece it is seeking in and caches a few nearby pieces. Each sample holds until the next timestamp, and the last one can hold through a longer audio stream. Chromium can settle a seek's clock while both the native callback and a snapshot still carry the old picture. The bridge compares both with the expected sample before it replaces the last canvas and acknowledges the seek. If Chromium cannot supply that sample at an MP4 endpoint or late in an HLS interval, the bridge seeks inside that sample while continuing to report the same requested time to the runtime.

## Colour grading

A clip's grade is HyperFrames' own `data-color-grading` on its `<video>` or `<img>`, so the runtime's shader draws it in the preview, `timeline_view` and frame capture alike, and Cutroom adds no second engine. `src/shared/timeline/grade.ts` holds the part of that format Cutroom edits: basic correction (`adjust`), the shadows, midtones and highlights wheels, master and per-channel curves, hue curves, up to four qualified secondaries, a look LUT, and an overall `intensity`. Every value is a bounded number, and the whole grade also passes HyperFrames' `validateColorGradingContract`, so a duplicate curve point or a soft range with min over max is refused as an edit. A grade that changes nothing is no attribute at all. An authored grade with anything else in it (a preset, grain, vignette, an effect, a variable, a colour group) reads as `grade: null` with `sourceRestrictions.grade`, and stays as written.

The runtime grades the picture the browser decoded: 8-bit RGB through the file's BT.709 or BT.601 matrix (its tags, else #136's rule for an untagged stream), limited range expanded to full, gamma-encoded as displayed. Every stage works on those display-referred values, in the order basic, wheels, curves, hue curves, secondaries, then the LUT, mixed with the source by `intensity`. Exposure is stops of gain on the encoded signal, not on scene light, as on a Rec.709 timeline in Resolve. Curves and the LUT are 8-bit textures in the shader.

`bakeHfColorGradingCube` runs the same stages on the CPU, texture rounding included, into a `.cube` with red varying fastest. `grade_save_lut` writes one into the project's `luts` folder at 33 or 65 points, for other clips or another editor. The direct export accepts a graded clip when its grade is colour only. The worker bakes each distinct grade once at 65 points into its scratch folder, converts the decoded picture to 8-bit RGB with `accurate_rnd` and `full_chroma_int` (FFmpeg's default conversion reads half a level darker than Chromium, and a grade's contrast doubles that), applies `lut3d`, and writes the same tagged BT.709 limited-range 4:2:0 as every other part. On a placed clip the grade comes before crop, scale and opacity, as the runtime grades the element's own pixels. The footage pipeline and timeline filmstrips share a project cache of colour-only grades baked by the same engine. They reuse in-progress requests and keep up to 256 saved cubes, about 35 MiB. The footage compositor uploads the 33-point RGBA8 LUT as a WebGL2 3D texture and samples it once after YUV conversion, before brightness and opacity. A slider draft uses 17 points so a move can reach the picture while the worker bakes the next one. The baker computes each wheel’s hue direction once for the whole cube. The draft cache and the compositor each keep the 16 most recent grades. Filmstrip tiles are shaded in a separate worker. The timeline budgets 32 MiB for graded tiles, reserving room for visible tiles before it prewarms the canvas outside the view. A tile holds its previous grade until the replacement is ready. Clips with spatial stages stay with HyperFrames in the viewer and go to frame capture for export. Videos drawn by the pipeline stay out of the runtime grader while parked.

Frame capture grades the pixels from HyperFrames' injected video frame and reads the animated opacity from the source element. Once the grading canvas takes over, the injected image stays available to the shader and stops painting beneath it. This gives each shot its own grade before the transition blends the pictures.

On a synthetic chart graded with a LUT, basic correction and curves (`tests/grade-render.test.ts`), the direct export differs from `timeline_view` by a mean of 1.4 levels in 255 and at most 12, through two 4:2:0 encodes; the ungraded picture is 27 levels away. Inside the chart's bands, the preview and frame capture differ by about 1.5. The grade baked into a 65-point LUT and applied as the only stage differs from the grade itself by a mean of 0.5 and at most 7.

The Colour section previews a control as it moves without saving it. The draft goes to the footage pipeline and the preview documents. A native clip's bridge writes the draft attribute, drops any paused hold copy that would cover the graded canvas, and redraws the selected clip. The attribute observer skips the change the bridge already drew. The native renderer uses video frame callbacks for playback and skips the additional redraw from the video's time update event. The bridge remembers the saved value, so its structure comparison reads the document as saved. Shift+D disables the compositor's LUT and uses the runtime's compare for its clips, showing the source across the whole picture. A saved grade change adds a graded element the live timing update does not take, so the viewer loads the saved document behind the shown picture, as for other non-timing edits.

`.cube` files are untrusted input. `src/server/grade/luts.ts` reads at most 16 MB of strict UTF-8: one 3D table of 2 to 65 points per axis with exactly that many rows, every domain and table value finite and within ±4. It then writes its own canonical copy (title, size, domain, rows at six decimals) under a fresh name in `luts/` through `projectWritePath`, so nothing else in the file reaches the project. Parse errors name the line, never the text on it. The editor uploads a chosen file; `lut_import` reads a path on this computer, outside the project, so it always asks. A grade names its LUT relative to the composition, as `src` names media, and the runtime loads only same-origin files.

Adjustment clips store the same grade attribute as pictures. The footage pipeline composites the lower video tracks and applies the adjustment as a GPU pass before drawing higher tracks. A single full-frame, ungraded shot can apply the layer's LUT in its picture draw. The native viewer and browser renderer use HTML-in-Canvas to capture the lower tracks, then pass their composite to the same HyperFrames colour renderer used for individual clips. Electron and the still-frame capture worker enable `--enable-blink-features=CanvasDrawElement`. The pinned HyperFrames export engine uses `--enable-features=CanvasDrawElement`. Electron 45.2.3 embeds Chromium 156.0.8078.80. The browser test draws a dissolve and a title and compares pixels with MP4. It passed on Chromium 155.0.8059.84 and runs in CI against the browser installed by pinned Playwright. The desktop colour check verifies the API in Electron after upgrades. When a headless browser lacks the API, the render reports an error at the affected frame. A plain browser shows a viewer notice when both its native capture and the footage pipeline are unavailable. [HTML-in-Canvas proposal](https://github.com/WICG/html-in-canvas)

When the direct exporter can draw the lower composite, FFmpeg applies its adjustment LUTs in track order after clip grading and placement. When the lower composite needs the browser, only those runs use capture. The browser extracts source frames for its capture runs on demand. HyperFrames selects its capture method once per render job. A graded adjustment in the composition or a mounted scene switches that job's browser frames to screenshot capture, including frames outside the adjustment or in a marked range that excludes it. MOV, WebM and GIF always render through the browser, so this affects their whole export range. The native viewer captures at the displayed picture's CSS-pixel size during playback. Pausing restores the displayed device-pixel size, capped at the composition size times device pixel ratio. Paused timing edits restore the original DOM while applying the edit and regroup before confirming the picture. The compiled preview only includes the capture controller for documents containing an adjustment clip, including mounted scenes. Adding the first layer loads its controller with the new document. The controller indexes layer start and end times, and only changes the groups when the visible layers change. The GPU compositor creates its separate adjustment pass on demand. The existing mixed MP4 export encodes eligible source frames directly, then stitches the runs in timeline order. ## Background mattes

Remove background cuts a clip's subject out with `u2net_human_seg`, the model `hyperframes remove-background` uses. Cutroom runs it itself from `src/server/matte/`. The CLI turns a whole file into full-resolution VP9 alpha, while Cutroom needs a source range it can stop and keep, and the raw mask.

A matte is the model's 8-bit mask of a range of source frames, stored in an ordinary visible `mattes` folder beside the composition, like `luts`, and named after the source and range (`mattes/interview 00-00-00 to 00-00-06.mp4`). It is H.264 in MP4, limited-range luma, at the model's 320x320 output, with no B-frames and a GOP of 30, so the footage pipeline's MP4 demuxer and WebCodecs decoders can read it like any source, and FFmpeg can read it for export. Matte frame `j` is source frame `first + j` on the grid `start + k / rate` that the pipeline and export read the source on (`frameGrid`). The rate stays a fraction as FFmpeg reads it (`30000/1001`, never a rounded decimal), and a constant-rate file counts its frames from the container, so a clip that plays to the source's last frame is matted to it. A variable-rate source is read at the slots of its average rate. `mattes/mattes.json` lists each matte: its source, the source's size and modification time, its first frame, frame count, grid and model. A matte whose source has changed is stale and is remade, and its entry is dropped when the new one is recorded. If a range has no subject (the model's peak probability stays under 0.2 in every frame), it is recorded with `subject: false` and no file, so it is not run again until the source changes. Jobs never write the composition.

`createMatteService` queues source ranges in the order asked and runs one job at a time across every project. A request queues only frames that no fresh matte and no live job cover, and a range that failed runs again only with `retry`. Each job is a worker process at nice 10. FFmpeg decodes the range (an accurate seek half a frame early, one picture per frame), scales it to 320x320 RGB, the model runs with four intra-op threads, and a second FFmpeg encodes the masks. Stop finishes the file with the frames already made and records them, so asking again makes only the rest. Requests for one project run one after another, so two at once never queue the same frames twice. A job that fails for any reason, the project folder disappearing included, ends as that job's error, and lines a model prints to stdout are skipped. FFmpeg writes each matte into a hidden file the service creates exclusively, which is renamed to a free name when it is done, so a link planted at a matte's name is never written through. Manifest entries can only name files directly in `mattes/`, and remaking a replaced source's matte deletes the stale file. Jobs wait as `needs-model` until the weights are on disk.

The weights and runtime are HyperFrames': `background-removal/models/u2net_human_seg.onnx` (168 MB) and onnxruntime-node 1.21.1 under `optional/`, in `HYPERFRAMES_CACHE_DIR` or `~/.cache/hyperframes`. A model the CLI already fetched serves Cutroom too. Cutroom downloads the weights only when someone presses Download (`POST /api/cutroom/mattes/model`): into a partial file, which is renamed into place only once it has exactly the model's 175,997,641 bytes and its pinned SHA-256. A download that runs past that size is stopped. The weights on disk are checked against the same digest, once per file version, so a truncated or altered file brings back Download. Like transcription, it never installs a runtime.

- `GET /api/cutroom/projects/:id/mattes` returns the model state and the project's jobs (`MatteStatusSchema` in `src/shared/matte.ts`).
- `POST /api/cutroom/projects/:id/mattes` with `{src, from, to, retry?}` queues the missing frames between two source media times.
- `DELETE /api/cutroom/projects/:id/mattes/:job` stops a job.
- The project event stream sends the same status as a `matte` event, coalesced to at most four a second.

On an i5-14400F without CUDA libraries, a 1080x1920 30 fps talking head mattes at about 3 frames a second, model load included, with a peak worker RSS of about 1.05 GB.

## Timeline engine

Copy snapshots the selected clips and linked partners through `/timeline/copy`, without a history write. The server retains the parsed source in a project-scoped session clipboard. The shared `paste` command reads that snapshot through `apply` options, mints fresh ids and links, and places the copied span at the playhead. Overwrite clears each picture or standalone audio interval on its source track. Linked sound uses the same routing function as media drops: replace the overwritten picture's partner interval, otherwise find a free picture-sound track for the whole sound span or create one. The editor selects every pasted clip, including linked partners, before the next edit. Insert opens the full span once with the engine's existing cut, ripple, and link checks. The source writer copies markup from the captured parse, so a cut or later source change cannot empty the clipboard. MCP uses `timeline_copy` and `timeline_edit` with the same command. The editor queues clipboard keys and makes undo wait for pending copy/cut/paste operations.

`move` defaults to overwrite, clearing only its destination spans with the same trim/split operation as overwrite inserts. All selected clips and their linked partners move before those spans are cleared, so the selection cannot erase itself. New pieces use the command's `ids` lists, including in the optimistic editor queue. `mode: "place"` keeps overlap refusal. The drag preview draws the engine result, including shortened clips, new tail pieces, and fully covered clips hidden until the drag ends.

`src/shared/timeline/` defines the timeline projection and command union as zod schemas, and a pure `apply(timeline, command)` that the browser and server share. Frames are integers at the root's `data-fps` (30 when absent). A value HyperFrames ignores, including decimals such as `29.97`, is refused instead of being read as 30, and NTSC spellings name their exact rate (`30000/1001`); HTML and `cutroom.json` keep seconds rounded to six decimals.

The editor compares the values of a clip's region when checking a queued edit against the server's answer. A region with the same settings can receive the next edit as soon as the first one saves.

Timing model: a clip spans the frames the runtime shows. Source offsets (`data-media-start`) are canonical at the microsecond: parsed once, and command inputs are rounded in the schema. Commands compute source times exactly from frame counts (frame rate as a fraction, times playback rate) and round once, when the timeline is written. Within one batch, 300 one-frame trims land on the same microsecond as one 300-frame trim. Separate requests each store six decimals, so repeated single edits can drift by up to half a microsecond per write; 300 one-frame trims sent one request at a time measured about 100 µs (10.999900 s against 11 s at 30 fps). The projected offset is the source time at the first shown frame; a start the editor wrote, within a microsecond of a frame, never shifts it, so a rounded NTSC start reads back unchanged.

A dissolve or dip belongs to the cut. The two clips keep their edit points, and the saved elements extend into the source handles so both pictures can run through the transition. When an in-point is on the edit's frame grid, Cutroom moves by whole frame indices before serializing the handle. Off-grid in-points keep their fractional offset. Frame capture restores the exact grid time for saved video handles before FFmpeg samples them, including handles written by older versions that rounded twice.

`src/server/timeline/` parses composition HTML and the `cutroom.json` timeline settings into that projection. parse5 builds the HTML spec tree, including implied end tags and foster parenting, and records byte offsets. One scope rule decides what a file renders, and the projection, the readback after an edit, and media discovery all use it: the entry `index.html` renders its live tree, where `<template>` content is inert as in the browser, and any other file is a sub-composition whose content is its first live `<template>` when it has one, as HyperFrames loads it. The offsets let applied commands become attribute edits, element removals, and inserted copies. An element is removed or copied only when it owns its source bytes: every start tag, end tag, and text in them belongs to its subtree, and its whole subtree lies in them. Otherwise the edit is refused, for example when a `<div>` written inside a `<table>` is moved out of it, text inside a table merges into the text before it, or a `</b>` inside the clip closes a bold begun outside it. Media without an authored duration is measured once per file version with ffprobe, using the media worker's shared protocol and container allow-list to reject playlists and indirect inputs before they can open other files or network URLs. The parser projects source restrictions for copying and removal onto each clip. The shared engine uses them for both optimistic edits and server commands. An auto-select razor cuts the supported targets and leaves restricted clips and their linked partners whole. Named razor targets remain explicit unless `autoSelect` marks a frozen auto-select list. Removing time through the middle of a text element or still image shortens it in place, preserving its id, start, text and agent attribution. Video, audio and sub-compositions still split to preserve the different source content on either side. Overwrites and explicit razor cuts keep their existing split behavior. Ripple edits refuse the entire batch when a participating clip cannot be cut or removed exactly. A copy restriction does not block shortening a spanning text element or still because it creates no copy. The refusal names the clip and track and suggests turning off auto-select on that track to leave it untouched. The razor command response reports `skippedClips` with clip ids, labels and reasons, including through MCP, and the editor counts cut clips and names those left whole in one informational status. All accepted changes remain one batch and undo step. The result must parse back to exactly the applied timeline content before it is written; source restrictions are derived again from the written document. `POST /api/cutroom/projects/:id/commands` applies a batch in one store mutation and history window; the revision covers the HTML and its settings. The existing apply pass names each command from its immediate before-state. Generated labels truncate at code-point boundaries, and the response summary header is encoded before any edit is saved. Agent-supplied labels remain literal text, limited to 120 characters, and appear after the factual outcome as `Agent label: "..."`; they never replace it. The MCP `timeline_*` tools call the same routes. A clip id is spent for good: before a batch or a script cut writes, every id in the timeline before and after it is added to `.cutroom/ids.json`, which lives outside undo history, and `apply` refuses a named id in that list and generates others around it. Undo and redo swap whole files and never consult it, so a clip they bring back keeps its own id.

A clip with versions is one host element: its ordinary `data-composition-src` (or an image's `src`) names the active version, and `data-cutroom-versions` holds every version's name and file as JSON. HyperFrames ignores the list, so the compiler, renderer, linter and media discovery see only the active file, and every timeline edit carries the list as it carries any attribute. `src/server/timeline/versions.ts` reads the list back only when it parses and includes the file the host shows, so a hand-edited `src` outside it reads as no versions. A switch rewrites the host's source and the scene's `data-composition-id` and size, read from the version's file. Version files are checked like scene files, and must also be outside hidden folders.

Media versions extend `data-cutroom-versions` with source frame offsets. The active index distinguishes two versions with identical sources and offsets. Only the shown source and In are written to the playable media element and its linked sound. Fit and availability come from the timeline’s media probes, so a remove or trim can disable an alternate without editing the list. The viewer keeps the saved take, the shown take and the playable rows either side of it ready while the list is open. GPU playback warms only the next row until the first hover. The document carrying a clip's takes starts loading when the pointer reaches its versions button. Native playback parks and unloads the other takes. Track metadata in `cutroom.json` includes name, kind, lock, auto-select, enable, mute, solo, and gain (`volume`, linear, 1 when absent). UI and MCP video inserts split sound into a muted video and a linked `<audio>` with matching source offset and duration by default. `Insert.linkedAudio` can name the partner's id; callers do not need to request separation. With `linkedAudio.track` the sound goes to that audio track and is edited as the picture's track is: overwrite clears its interval there, and insert adds the track to the rippled set. Picture visibility and sound suppression are separate. Disabled tracks hide picture; mute suppresses every sound on its track, including embedded video audio in hand-written compositions. Splits, moves and undo preserve these distinctions. Solo persists in `cutroom.json` and is undoable so preview and export use the same mix, as recorded in the project plan. These controls use the same commands and readback through MCP. The viewer's master mute remains local monitoring state and does not change export. Export shows a one-line notice identifying soloed or muted tracks. Preview readback and render preparation reapply the saved mix to outside HTML changes in memory, including each bundled scene instance. Render workers receive those effective sources before static parsing and browser discovery. This adds no source writes or undo entries.

Track gain is an independent HyperFrames `<hf-audio-group>` stage. Each audio track, and each video track carrying embedded sound, gets a playback bus. Routing is persisted when a track fader is first used; unrelated edits at unity leave authored source alone. The bus is marked `data-cutroom-track` with the track index. Its `data-volume` is the track's linear gain. Clips join through `data-audio-group`; their own `data-volume` stays canonical, including outside source edits. A subsequent track gain change edits only the bus attribute, regardless of clip count. Preview preparation supplies unity buses before first use. When membership is first saved, existing generated media identities are pinned with `data-hf-id`, so routing does not change the playing clip's identity. The shared mix pass reconciles membership after insert, split, move and paste, removes buses for removed tracks, and runs for preview and render preparation. The gain line is drawn on one scale down the clip body, `scaleOf` in `mix.tsx`. Its stops depend on the body's height in pixels: +12 dB at the top, 0 dB 3 px above the middle of the body, -6 dB 3 px below it, -24 dB at 94% and silence at the bottom, in straight runs between. The middle is kept clear because that is where a clip is grabbed to move it: the middle of the clip's box is 5.5 px above the middle of its body at every height, and the line's grab band, `.tl-gain`'s stroke, is 3 px. At unity the band lies between the two middles with a pixel to spare on each side, and from -6 dB down it is a pixel or more below both, so a press on either middle is a clip move at unity and at any level a music bed sits at. The 18 dB from -6 to -24 dB take everything between the lower clearance and 94%, which is the most room that constraint leaves. `mixBody` gives the body's height for a track, and both renderers of the line, `ClipMix` and the drag preview in `lanes.ts`, use it. The waveform is scaled by the root of the same gain, since peaks are drawn on a square-root scale, and `waveformScale` holds that at a third so a clip turned far down still shows its beats; a fade multiplies the floored value, so it still tapers to nothing. A gain drag reads that scale back, so the line stays under the pointer from the first vertical pixel. Until the press has travelled the 3 px drag threshold that gain is only shown: the gesture is `loose`, and at the threshold it becomes a locked gain drag or, if it went sideways, the usual clip move with the gain taken back. A loose press released within 250 ms that stayed inside a 1 px box, or that ends where it began, is a click. It reads the drawn envelope where the line was pressed, through the fade and any volume lane there, and stops at the gain that can be reached. A line within half a pixel of unity lands on unity. Shift is 0.1 dB per pixel at every height. A change of Shift takes hold of the line again at the gain it shows, so later travel starts from there without a jump, while Esc and undo still return to the gain the press found. Gain remains one command and undo step on release; fades still use timeline frames per horizontal pixel at the current zoom. Clip mixing uses HyperFrames' native attributes. `SetClip.volume` is linear gain, with unity at 1 or null and the core `MAX_AUDIO_GAIN` ceiling at +12 dB. `SetClip.fadeIn` and `fadeOut` are authored integer timeline frames, projected from `data-fade-in` and `data-fade-out` seconds. Writes retain microsecond precision, so even a one-frame NTSC fade reads back exactly. Reads and fade edits preserve authored lengths, including lengths beyond the clip. Ordinary edge trims, including rolls and the edited edge of Q/W, never rewrite native fades. Preview, render, display and handles use core `clampFadesToDuration`, which scales both fades proportionally when their sum exceeds the duration. Splits, overwrite and ripple cuts instead preserve the surviving source envelope without adding fades at internal cuts. A truncated or proportionally scaled ramp becomes HyperFrames native `data-automation` volume breakpoints, retaining its original endpoint beyond the piece so an extension cannot hold a mid-fade level. Existing volume automation is multiplied into those breakpoints, and other lanes retain their targets. On a head cut or trim, clip-local automation moves with the surviving source. Native automation cannot retain points before the new start, so head trim and extension of a baked ramp can lose its earlier envelope; source-anchored envelopes are deferred to keyframes. FX attributes are left intact; clip gain and fades multiply the runtime's resolved level. A GSAP tween on volume retains HyperFrames' absolute-volume semantics and can override static clip gain.

Drag readouts stay inside the visible timeline.

Gain and fade handles use the existing gesture state machine, shared engine preview, frozen clip snapshots, and single command batch on release. A predominantly horizontal drag at the 3px threshold becomes a clip move and keeps that intent until release. Fade drags start at the effective handle rounded to a whole frame. Handles meet but never cross, and on a clip shorter than its authored fades the other edge is committed at its drawn length so it stays in place; a drag back to its start writes nothing. The clip's SVG draws native volume automation at the gain line's level. Without automation, only the fade knees and endpoints need path vertices. Gain overlays mount at the same 28 px width threshold as clip names; narrower clips cannot fit both trim edges and fade handles. Fade drags never change automation: HyperFrames' format can't tell a ramp Cutroom baked from one an author drew, so removing it is always explicit. ## Fonts

`src/server/fonts/` adds fonts to a project for the inspector's Add font dialog and the `fonts_list` and `fonts_add` tools. Every added face is a file in `assets/fonts` and one `@font-face` rule in the `<style data-cutroom-fonts>` block of `index.html`, which Cutroom creates in the head on first use and only appends to. `declaredFonts` reads that block like any other, so the family joins `timeline.fonts` with the next timeline read, and HyperFrames' deterministic font pass finds the face declared and fetches nothing at render time. A family `index.html` declares outside the block is refused, so an added face never shadows an authored one.

The rule is generated, never copied: the family passed the `fontFamily` schema (letters, digits, spaces, hyphens, underscores), the weight is a number and the path is Cutroom's own `Family-700.ttf`-style name, so a rule cannot carry a quote, `url()` or markup. Files are written with `wx` through `projectWritePath`, taking the next `-2` name rather than replacing a file, inside the project's history window, so undo removes them with the rule. If the `index.html` write fails, the files this call wrote are deleted.

`fontFile.ts` checks a file's signature (TrueType, OpenType, WOFF, WOFF2; collections are refused) and reads its `name`, `OS/2` and `fvar` tables, inflating WOFF tables and the WOFF2 Brotli stream to at most 80 MB. The family is name ID 16, then 1, cleaned to the schema's characters; a variable font's `wght` axis becomes a weight range. `google.ts` reads Google's catalogue once per server (dropped on failure, so the next request retries), builds the CSS API URL from a catalogue family and weights from 100 to 900, and sends a fixed non-browser user agent, which gets one whole TrueType file per weight rather than per-script subsets. Each file URL must match `https://fonts.gstatic.com/s/<family>/v<n>/<name>.ttf` before it is fetched. Redirects are refused, replies are read to a byte limit, and every download finishes before anything is written. Tests pass their own `fetch` to `createGoogleFonts`, so CI never reaches Google.

## Voiceover

`src/client/voiceover/` owns one armed microphone for the open project. The device id stays in local storage, outside project history. Pressing Record while idle picks the first unlocked audio track free at the playhead, reserving a new track when needed, then arms and starts recording. One informational line names the destination. A new track is persisted only when the take is saved, in the same undo step as its clip. Arming opens `getUserMedia` with mono audio and speech processing disabled. An AudioWorklet transfers 2,048-sample PCM blocks with their audio-clock frame, independently of the UI thread. Only the short pre-roll stays in memory while armed. During a take, blocks accumulate for at most 30 minutes. The header reuses the timeline meter with a compact mono layout and microphone samples; levels stay outside React and the recording indicator is static. A voiceover-coloured take region grows from its start to the playhead with one scale transform; the transport and armed R use the existing danger colour, separate from the playhead. Switching projects or editors is refused while recording, saving, or retaining a failed save. The user must save or discard the take first. Browser close/reload uses beforeunload, and the desktop keeps its window and backend open until the take is resolved. Leaving an armed track releases the stream and audio context.

The session transition table distinguishes idle, arming, armed, recording, saving and save-failed. While arming or armed, the session follows the timeline store: removing its track through the UI, MCP, history or outside edits transitions to idle and stops every microphone stream track. An opening microphone from an earlier arming attempt is closed when it arrives. The initial A1 placeholder can still be armed before an audio track is persisted. Device release is separate from take resolution: a disconnect keeps saving or save-failed and its navigation guard. Retry and discard return to armed only if the microphone is still open, otherwise idle.

Recording starts normal forward playback with looping temporarily off. The preview sends continuous playback seconds paired with its absolute performance timestamp. The first advancing playback observation anchors the audio sample window, and the parked playhead sets the take's end; microphone capture never assumes playback started at the record button's wall time. AudioContext.getOutputTimestamp pairs the sample clock with performance time; currentTime can advance in device-sized batches. The capture window maps the preview observation through that pair, accounting for message delivery time, and advances by the device's reported input latency plus the audio context's base and output latency. Output latency is read again when each take starts. Cropping uses sample frames, without rounding compensation to video frames, and waits for the delayed tail before saving. A device that does not report input latency is labelled as such; only output delay is compensated in that case. These browser-reported delays cannot establish the accuracy of a physical microphone or output driver's latency report. A playback-anchored click train checks saved PCM positions within 1 ms, or 48 samples at 48 kHz. This catches capture-window errors separately from export placement.

The fake-microphone test compares every saved sample with a separate raw-input worklet tap, within one PCM quantization step, and requires export placement within one video frame. A source-file correlation after the fake device's startup checks that it supplies the intended signal. Pinning Chromium to one CPU reproduced 420–421 zero PCM samples around 180–210 ms in the raw input itself, before Cutroom's buffering or alignment; a 30-second source rules out looping. The test retains that input artifact in its reference rather than trimming or relaxing the saved-sample check. Missing render quanta remain gaps in the worklet's block timestamps, including inside a partial block, so WAV assembly reports dropped audio instead of joining samples across a gap.

Takes are mono 48 kHz, 16-bit PCM WAV in `assets/voiceover/`. PCM adds no codec delay or lossy encoding, works with the existing audio probe, peaks, preview and export, and uses about 5.8 MB per minute. Upload uses the existing media endpoint; placement batches `setTrack` when needed and `insert` through the normal timeline queue. The armed track receives the take when it has room for the full range. An occupied, locked or repurposed destination falls back to the first unlocked audio track with room, creating one only when needed. The live take uses the same destination rule as placement and shows a new lane when needed. The whole placement is one undo step; media files remain. Missing PCM blocks stay silent at their sample offsets, and a toast reports the dropped duration after saving. A failed upload or placement retains the take and opens the input panel with Retry, Download, and a confirmed Discard. The recording key explains a pending save or recovery instead of silently ignoring it. Escape stops the take and opens the app discard dialog; cancelling saves it. Recovery stays marked on the microphone after the panel is dismissed, and opening the panel moves focus into its controls. The session clears only its own toasts when their conditions resolve.

The engine exposes `kind: "voiceover"` through the same schema and MCP timeline readback as other clips. On disk it is a regular `<audio data-cutroom-kind="voiceover">`, so the renderer needs no new media type. Audio editing rules use `isAudioKind`, and the timeline uses the existing voiceover colour tokens. No new MCP tool is added. Electron allows audio capture only from the editor's main frame and continues denying camera and preview-frame capture.

## Rendering and transcription

Preview and export use the public HyperFrames compiler and renderer. Export runs in an isolated Node worker because the producer's Node HTTP adapter modifies globals that Bun's server also uses. Keep `renderWorker.ts` beside `jobs.ts` when packaging. Cancellation waits for the owned process group and partial-output cleanup before shutdown completes.

Thumbnails and MCP `timeline_view` use the same capability-scoped, opaque documents as the new viewer. The frame extractor transform gives SDR video the colours Chromium draws: untagged fields take Chromium's BT.601 or BT.709 guess, and BT.601 primaries or other non-sRGB transfers are converted to sRGB before frames reach the page. On Linux, exports and frame captures prefer the Chromium binary under `/usr/lib/chromium`. Set `HYPERFRAMES_BROWSER_PATH` to a different browser binary, such as Playwright's installed Chromium, to override discovery.

On Linux, export and still capture add `CDPScreenshotNewSurface` to a single `--enable-features` list. This preserves HyperFrames' `CanvasDrawElement` and any other enabled features. The still browser also keeps its `--enable-blink-features=CanvasDrawElement` switch. Screenshots request a fresh compositor surface after the timeline seek and image decode. The legacy redraw callback can take about two seconds per frame in full Chromium. [Capture timings](performance.md#chromium-screenshot-capture).

Frame-capture Chromium is reused by thumbnails, note images, and `timeline_view`. `captureBrowserWorker.ts` owns that browser through a DevTools pipe. Chromium exits when that pipe closes, including when SIGKILL kills the owner alone or the server's whole process group. Chromium also exposes an ephemeral loopback WebSocket endpoint, published through `DevToolsActivePort`, so the server can keep using Puppeteer directly without relaying capture traffic through the owner.

The upstream thumbnail coordinator admits one capture at a time. The thumbnail API hashes `thumbnailRendererVersion`, the caller's version, and the exact seek time into Studio's cache version. Nearby seeks stay distinct even when Studio rounds them to the same cache time. Bump the renderer version to invalidate existing captures without deleting their cache files.

The renderer keeps its last successful page loaded so the next uncached frame of the same composition only seeks, which brings a warm `timeline_view` frame from about 300 ms to about 120 ms (700 ms to 170 ms on a 500-clip timeline). A page is reused only when the preview URL and viewport match and the project signature the preview route stamped into the document equals a fresh signature of the files on disk; anything else, including an edit that a file watcher has not reported yet, loads a new page. Render edits are injected once per page, since they wrap seeking and expose re-apply hooks the capture calls every time. Failures, diagnostics, and cancellation close the page instead of keeping it, and an idle page closes after 30 seconds or on disposal, so at most one loaded composition is retained. Each page opens in its own headless window: tabs in one window pause animation frames in all but the newest, which would stall readiness for a page opened beside the retained one.

Each page waits for load, then checks the runtime's `__renderReady` flag inside the seek evaluation. Capture uses the viewer's paused seek to confirm the decoded picture at the requested frame. This also covers 59.94 fps steps, which can be shorter than the runtime's native seek tolerance. Ready scenes need no polling setup. Load alone can precede authored scripts, sub-compositions, or declared `__hf.buildReady` setup; an early seek can otherwise return time zero. Pending readiness polls on animation frames, with a 20-second timeout that names the composition. `__hfStartupError` fails the capture rather than caching an incorrect image. MCP `timeline_view` forwards cancellation through its timeline read and image fetch, so cancelling a never-ready scene closes its page and frees the queue. The page awaits the seek and seek completion, waits for fonts, applies render edits, and paints before taking the image. Editor PNG downloads and note images use this same path. MP4 exports use the producer's separate readiness gate, whose reported duration stays zero until `__renderReady`. Captures do not wait for network idleness: unrelated composition background requests must not hold every later capture. A cold browser, media decoding, or captures already ahead in that queue can still take longer than a second; notes save independently and retain their static placeholder while waiting.

The server closes the owner's IPC channel on renderer disposal. The OS also closes that channel whenever the server process ends, so a surviving owner closes Chromium, waits for it, and removes the profile. The owner handles SIGINT, SIGTERM, and SIGHUP too. A five-second fallback still kills Chromium's process group if graceful close stalls. On Windows it kills only the root process. A stopped browser cannot process pipe closure, so Puppeteer's detached browser group remains necessary for that fallback.

Capture profiles are named `cutroom-capture-<owner PID>-<random suffix>` in the temporary directory. On Linux, still captures fall back to `/tmp` when Chromium's singleton socket would exceed the system's path limit. Exports use a short path to their on-disk scratch in that case. A new owner sweeps only matching directories whose PID no longer exists. Live owners, reused PIDs, unmarked directories, and symlinks are preserved. The PID is part of directory creation, so a killed owner cannot leave a new profile without an owner marker. SIGKILL can leave the profile until the next capture owner starts; graceful shutdown removes it immediately. Playwright sends SIGTERM and waits for cleanup before escalating. Keep the worker and `ownedDirectories.ts` beside `captureBrowser.ts` when packaging.

Local transcription uses an already installed Whisper runtime and complete model. It runs outside the project in a temporary working folder, then imports normalized words through a history transaction. Job cancellation and shutdown await cleanup before closing project histories.

## External agents

Both MCP transports forward to the running server. They do not open a second project store or write files independently. The server binds to loopback and rejects foreign browser origins and rebinding hostnames. This endpoint is intended for agents on the same machine, not public network exposure.

Mutating editor and upstream routes require an exact allowed Cutroom `Origin`. The loopback `/mcp` endpoint also accepts native HTTP clients that omit `Origin`. If a client sends an opaque, foreign, or wrong-port origin, the server responds with 403. Both MCP transports supply the selected server origin when forwarding requests. Development additionally permits the two explicit Vite origins.

Path-based media import uses a Unix socket under the Cutroom data directory. The socket trusts processes running as Cutroom's OS user. Electron supplies paths from disk-backed files selected or dropped by the owner. The stdio bridge pre-checks that it can open each source and sends its stat identity. The server opens the source and checks that identity again before linking or copying. The TCP listener has no path-import route, and the web server still starts if the Unix socket is unavailable.

## Background jobs and timeline media cache

Render, transcription, waveform, scrub-audio, filmstrip, scrub-proxy, and precise-frame jobs use `src/shared/jobs.ts`. Jobs move from `queued` to `running`, then `done` or `failed`. Cancellation enters `cancelling`, then `cancelled` only after cleanup succeeds. Cleanup failure takes precedence over cancellation and enters `failed`. Render and media cleanup errors also propagate through their cancel/shutdown calls. Running progress uses 0 to 1. The render adapter preserves `rendering` / `complete` and 0 to 100 progress; transcription preserves `running` / `complete` and 0 to 1. Transcription MCP status forwards the same HTTP response; there is no render-status MCP tool.

The migration also fixes main's HTTP render-cancel bug. Upstream assigns `status = "cancelled"` before invoking `cancel()`. Main's old cancel guard then returned without stopping the worker. The adapter now translates that assignment into the cancellation transition, keeps the HTTP status `rendering` during cleanup, and lets the route await cancellation. Cleanup errors return a failure instead of claiming the partial export was removed.

### Media endpoints

The project file listing includes `fileVersions`, and workspace file-change events include the same stat-derived `version`, or null for a removed file. Media thumbnails and probes include it in their URLs. The timeline listens without a React render, aborts pending loads and releases decoded pictures and peaks when a used source changes, then redraws from versioned URLs. Unrelated file changes keep the decoded cache. The shared fingerprint preserves the existing review-mark format.

- `GET /api/cutroom/projects/:id/media/probe?path=...` exposes the existing cached media probe. A ready response contains audio `channels` and video dimensions, frame rate, and duration when present. The Media panel uses channels to decide whether a video drop needs linked audio. It follows the same 202/job lifecycle as the preview assets.

- `GET /api/cutroom/projects/:id/media/peaks?path=...` returns the complete binary cache file. Add `level`, `start`, and `end` to stream just one mip level and time range. Times are seconds; end is exclusive. Buckets intersecting the requested range are included. Defaults are level 0, start 0, end of media. A nonexistent level or reversed range returns 400.
- `GET /api/cutroom/projects/:id/media/pcm?path=...&v=...` returns the source's [scrub audio](#scrub-audio-format), honouring byte ranges. As on the other media routes, `v` is the listing's file version, which keeps browser caches of different versions apart; the server fingerprints the file itself: source sample `k` is bytes `2k` and `2k + 1`. A range past the end stops at it; one that starts past the end answers 416.
- `GET /api/cutroom/projects/:id/media/filmstrip?path=...` returns version 2 metadata with `interval`, `tileWidth`, `tileHeight`, `count`, `key`, and `sheets`. Each sheet has `index`, `start`, `count`, `columns`, `rows`, and `spriteUrl`. Tile indexes run left to right, then top to bottom, within a sheet. The final row may contain black unused cells.
- `GET /api/cutroom/projects/:id/media/scrub?path=...` returns the video's [scrub proxy](#scrub-proxies) as an MP4.
- `GET /api/cutroom/projects/:id/media/proxy?path=...` returns the video's [editing proxy](#editing-proxies) as an MP4, with byte ranges, or 422 for a video the browser decodes itself.
- `GET /api/cutroom/projects/:id/media/source?path=...` returns an MP4, M4V or MOV file's own bytes, honouring byte ranges, for the [footage pipeline](#footage-pipeline). Other file types and anything in a hidden folder answer 404, including through a link.
- `GET /api/cutroom/projects/:id/media/frame?path=...&time=...` returns a small JPEG at the requested source frame. Time is quantized down to a frame using the probed native frame rate. The cache key includes that frame index, so requests for the same frame share work.

These endpoints return `202 {key, job}` with `Retry-After: 1` and `Cache-Control: no-store` while preparing. Poll the same URL. Shared source probing is itself a queued job; its key may be replaced by the asset job's key on a subsequent poll. Failed jobs return `422 {key, job}` with an error, remain visible for thirty seconds, then permit retry on the next request. Missing audio/video streams are rejected with 422 from the cached probe information, before an asset worker starts. Editing the source changes its fingerprint and permits an immediate retry. Missing FFmpeg or ffprobe returns 503. Source-path responses use private revalidation ETags; matching `If-None-Match` returns 304. Peak ETags include the selected level and bucket range. Key-addressed sheet URLs are private and immutable, with a sheet-specific ETag. Of these, agents see only the editing proxy's job state, in `media_list`.

### Scheduling and storage

Preview and render prepare authored local ramp audio with the same FFmpeg source clock and deterministic stretch. In the isolated preview, the warmed WAV replaces only the sound. A picture with embedded sound keeps its video source and rate lane and adds an audio element on the same clip clock. The audio graph still owns fades, gain and effects. Prepared files share the media worker queue and key by source fingerprint, input offset, clip duration, rate lane and recipe. The served preview's document record owns readiness and can recover a file evicted before its clip plays. The editor reads preparation status from the document's inspection reply even while the footage pipeline is attaching. The current player stays attached while the transport is running.

The service runs at most two media worker processes. Frame requests have the highest priority and run newest-first within that priority. Requesting an already queued frame again moves its shared job to the front. Probing and peaks follow, with FIFO ordering at their priority, then editing proxies, filmstrips and scrub audio, and scrub proxies last. Only one filmstrip, scrub audio or scrub proxy may run at a time, reserving the other worker for interactive work. A long clip plays from its editing proxy's pieces as they are made, so one editing proxy may also take that other worker. The preview waits on a proxy while a request for one of its pieces is open, or for 3 s after it last asked whether the proxy is ready. Among proxies, one the preview waits on goes first, the latest asked first. A proxy nobody waits on is background work: after its current piece it gives way to one the preview waits on, and to frames, probes, peaks and piece plans waiting for a worker, so opening a second recording does not wait for the first one's whole proxy. Each worker runs one FFmpeg or ffprobe process at a time. Decoding, min/max aggregation, and sprite assembly run outside the server process. On POSIX, the server owns each worker's process group and kills its FFmpeg descendants even if the worker crashes. Shutdown cancels queued jobs, terminates active groups, awaits all cleanup, and propagates cleanup errors before project histories close.

The cache lives in `<project>/.cutroom/cache/<key>/`. Its SHA-256 key includes the recipe version, output kind, canonical source path, size, nanosecond mtime/ctime, inode, and device. Frame keys also include the source-frame index. The shared `fileFingerprint` supplies the size and mtime identity used by review marks, project listings, watcher messages, and client media URLs. The server retains the additional nanosecond and filesystem identity fields for timestamp-preserving edits. This avoids hashing an entire large video before every warm response. Inode/device identify replacements whose timestamps were preserved, including copies from filesystems where ctime mirrors mtime. Identical copies may use separate cache entries. The source fingerprint is checked again before atomic publication. Complete directories appear by rename; temporary frame files are cleaned before publication. After publication the service keeps at most 256 completed artifact directories per project, oldest first, protecting active jobs. This also bounds files left by previous server runs. Entries are disposable. Timeline probes retain only the latest stat version per path, for up to 256 paths.

Paths and cache locations use the project boundary check, including symlinks. FFmpeg accepts local media demuxers, including MXF, Wave64, and CAF, while excluding playlists and network protocols. Frame patterns and sprite paths are relative to the worker's task directory, so a percent sign in the project path cannot become a pattern directive.

### Waveform format

The first audio stream decodes to interleaved signed int16 PCM at 48 kHz without downmixing. Each bucket takes extrema across every channel, preserving out-of-phase stereo and a one-sided microphone at full amplitude. Base buckets span 96 sample frames, or 2 ms. Mips reduce groups of four pairs until the first level covering the four-second target. Widths are 2, 8, 32, 128, 512, 2048, and 8192 ms. The final partial bucket and partial mip groups retain their samples. These constants live in `src/shared/media.ts`.

CRPK version 2 is little-endian. The complete file has a 144-byte header/directory followed by all seven level payloads. A ranged response has a 48-byte header/directory and only its selected pairs; it remains a valid CRPK file.

| Byte offset | Field                                                                                                               |
| ----------- | ------------------------------------------------------------------------------------------------------------------- |
| 0           | ASCII `CRPK`                                                                                                        |
| 4           | uint32 version, currently 2                                                                                         |
| 8           | uint32 number of levels in this response                                                                            |
| 12          | uint32 decoded sample rate, currently 48000                                                                         |
| 16          | float64 total decoded sample-frame count, including all channels once per frame                                     |
| 24          | uint32 base bucket width in sample frames, currently 96                                                             |
| 28          | uint32 first bucket index in the selected level, zero for a full file                                               |
| 32          | One 16-byte directory entry per returned level: uint32 sample frames per pair, pair count, byte offset, byte length |

Each payload pair is an int16 minimum followed by an int16 maximum. Normalize amplitudes by 32768. Duration is total sample frames divided by sample rate. For ranged responses, pair time is `(firstBucket + pairIndex) * sampleFramesPerPair / sampleRate`. The server reads the directory and streams only the requested payload bytes. A two-hour overview at the coarsest level is 879 pairs plus header, or 3564 bytes, instead of the roughly 19 MB complete file.

### Scrub audio format

Scrub and shuttle sound reads raw samples rather than decoding, so it can read any sample in either direction. The `pcm` job writes `audio.pcm`: the first audio stream (`0:a:0`) as headerless 48 kHz mono signed 16-bit little-endian PCM, FFmpeg's own `-ac 1` downmix. Sample `k` is media time `k / 48000` on the clock export seeks: a stream's timestamp less the earliest picture or sound's start, except that MP4, MOV, WebM and Matroska keep timestamps from zero, as browsers play those (`mediaClock` in `pictureIndex.ts`, shared with the picture index). The worker asks ffprobe for the first decoded frame's timestamp, writes the time from media zero to that frame as silence, rounded to the nearest sample, and appends FFmpeg's plain `-f s16le -ar 48000 -ac 1` extraction. A stream that starts after the picture, or an MP4 whose AAC priming has no edit list, still puts each sample at its media time. After the padding the file is that extraction byte for byte. A source at another rate can start between two 48 kHz samples; it then lands up to half a sample early or late. A timestamp gap inside the stream is not filled, as in the export mixer's own AAC reads.

The file costs 345.6 MB per hour of source. It is keyed by source fingerprint like the other artifacts and leaves the cache with them. On November 21, 2026, one hour of 192 kbps stereo AAC took 2.4 to 2.5 s from request to published file over three runs, and its FFmpeg pass used 4.1 s of user CPU (FFmpeg 9.0.2, 16 cores).

### Scrub and shuttle sound

The preview runtime plays sound only at 1x forward. Every other shuttle speed, forward and reverse, dragging the playhead and stepping frames sound through `src/client/scrubAudio/`, a separate Web Audio graph in the editor window that survives preview reloads.

- `plan.ts` turns the timeline into one segment per sounding clip: its output samples, its source, where each output sample reads that source, and its gain (clip gain, fades, automation, crossfades, track or bus, main; zero when muted or soloed out). The effects rack and nested compositions are not applied. The plan is rebuilt when the timeline or the file listing changes. Clips at zero gain are dropped and their audio is never fetched.
- `chunks.ts` reads the [scrub audio files](#scrub-audio-format) in 262,144-sample chunks (5.5 s, 512 KB) with byte ranges. It holds the chunks of the segments within 20 s of the playhead on either side, nearest first, and lets go of the least recently wanted past 64 MB. Chunks go to the audio thread and are not kept on the main thread. A chunk that has not arrived plays as silence; nothing waits on a fetch. A read for a chunk that leaves the window is cancelled. A source is read one chunk at a time until a chunk arrives: a file still being made (202) is asked for again each second, and a failed read (network error or 5xx) after a wait that doubles from one second up to 30. A file with no sound (422), or another refusal (4xx), is not asked for again until its version changes.
- `worklet.ts` is an `AudioWorkletProcessor` that holds the nearby segments and chunks and renders 128-frame blocks through the `Player` in `render.ts`, plain code tested without Web Audio that allocates nothing per block. Up to 1x either way it reads like tape, with linear interpolation, so 1x reverse is the forward sound backwards; a clip at another speed plays at that speed's pitch, as at 1x. At 2x, 4x and 8x it overlap-adds 40 ms Hann grains, each starting where the motion has reached (mapped through the clip's speed) and reading one source sample per output sample, so grains keep the source's own pitch; in reverse each grain plays backwards. A tape voice that reaches a chunk not yet held fades out over 1 ms and back in when it arrives; a grain whose source is not all held stays silent for its whole length. Up to 16 clips sound at once. Starting and stopping fade over 5 ms, and a new motion while sound plays (a speed change, a re-anchor, a drag or a step) crosses over from the old one in 5 ms, so none of them clicks. A drag plays as tape at any speed, up to 8x: each report of where the pointer is (`chase`) carries its speed, and the worklet runs at that speed and closes any gap to the pointer over 10 ms, so pitch follows the pointer and turning back plays backwards. A report more than 0.2 s of sound from the tape crosses over to it. When no report comes for a frame (at least 1/30 s), the drag fades out. A frame step (`frame`) plays exactly that frame's output samples once, fading in and out over 1 ms. With nothing to play, it returns at once.
- `engine.ts` follows the playhead the keys drive: `sourcePlayer` while the viewer shows a source, and otherwise the timeline transport. A source plays as one segment straight from its file, frame n at n frames into the file, at unity gain, with no plan, mix or effects; a file without sound has no segment and is never read. Showing the source or the timeline, or closing the source, stops whatever was sounding before the other playhead takes over. In `shuttle` it sends the worklet a motion: at a given audio frame, this output sample, moving this many samples per frame. The worklet then advances on the audio clock. The anchor frame is the one the output device plays at that moment, so sound lines up with the picture after the device's own latency. Until the context runs and its output clock has moved on from where it stopped (just after creating or resuming it), the engine sends nothing. It compares the sound with the transport's position between frames (`shuttlePosition`) at the same instant, and re-anchors when they differ by more than one frame or one display refresh of motion, whichever is longer: the playhead moves once per refresh, which at 8x spans several frames. In `scrubbing` it reports each frame a drag reaches with the pointer's speed, measured between frames and averaged with the last; a press, a move after 0.2 s still, or a change faster than 16x only marks where the pointer is, so jumping the playhead to a click is not heard as a sweep. Each frame step the transport counts (`steps`) sends that frame's samples; a step taken while the context starts plays if it is ready within 250 ms. In `playing` and `stopped`, and while the viewer is muted, it stays silent.

Audio scrubbing (Shift+S, `editScrubAudio`, and the waveform button in the tool row) turns drag and step sound on and off. It is on by default and kept in this browser's local storage with the other viewer toggles. Shuttle always sounds.

No `AudioContext` exists until the first shuttle, drag or frame step of the session. It is created with `latencyHint: "interactive"` at 48 kHz, so output samples are source samples, and suspended five seconds after the last sound, including when a shuttle ends before the worklet has loaded or the worklet fails to load. Once it exists, a playhead parked for 300 ms loads the chunks around it, so the next shuttle starts warm.

`window.cutroomScrubAudio` lets end-to-end tests read the context's state, the worklet's frames, motions, peak, last source sample and the lowest and highest read since the last probe, and when the latest shuttle, drag or step first sounded. In headless Chromium on November 22, 2026, the median of 30 J and Shift+L presses from the key event to the first audible block was 4.6 to 8.0 ms over 25 runs, before 24 to 48 ms of device latency. From a pointer move on the ruler to the first audible block, the median over 30 drags was 9.0 to 10.8 ms over four runs. In Bun, with 8 clips sounding, a 2.7 ms block took about 30 microseconds as tape and 50 to 75 as grains, and 140 during a 5 ms crossover, when both motions render. Headless Chromium's fake output clock runs about 0.35% slow against the page clock and moves its reported latency in 8 ms steps, so a long 8x shuttle there can re-anchor about once every second or two; a real device holds its latency steady.

Grains start where the motion has reached, not where the waveform best lines up with the previous grain, so a steady pitched sound can roughen at 2x. Aligning each grain to the previous one (WSOLA) is a possible follow-up once the owner has listened.

### Filmstrips and precise frames

Overview frames use keyframe-only decoding at the fixed two-second interval. A gap beyond the interval plus one source frame triggers per-tile seeking. Otherwise the worker keeps the keyframe tiles and seeks only missing tail slots. Seeks use source-frame boundaries so the last frame is available when the final tile slot lies within its duration. A long audio stream cannot add phantom video tiles; seeking stops when no video frame exists. Frames retain the source display aspect ratio, including pixel aspect and rotation, at a fixed height of 90. Width rounds to an even pixel count for JPEG. No portrait letterboxing is applied.

Sprites contain at most 100 tiles and ten columns. This bounds sheet memory and dimensions and removes the former two-hour single-sheet limit. Precise on-demand frames use accurate seeking rather than keyframe-only decoding, making shots within an overview interval reachable. Interval, height, sheet limits, and JPEG quality share the same constants used by the metadata schema and FFmpeg filters.

Run `bun run bench:media` to generate a nominal 60-second 1080p testsrc2/sine sample at 30000/1001 fps with a 60-frame GOP and a brief blue shot inside overview tile 0. The benchmark exercises the three endpoints cold and for 30 warm reads, checks the tile count against the probed NTSC duration, records per-mip bytes, range bytes, health latency and logical/allocated cache sizes, and captures a dark 1720-pixel-wide image. It also creates a lossless impulse fixture and draws a 32-pixel-per-frame crop at 60 fps beside the on-demand frame. The script prints its temporary output directory and retains all generated evidence.

### Scrub proxies

A seek in the source decodes from the previous keyframe, so on long-GOP 1080p footage one seek takes 50 ms or more, and a drag that asks for a new frame on every pointer move used to abandon each decode for the next: a 3 s ruler drag over a 1080p interview showed no new picture until the pointer rested. Each video in an open preview now gets a scrub proxy beside its filmstrip: the first video stream scaled so its shorter side is at most 540 lines, H.264 with every frame a keyframe, and the source's own timestamps, so proxy frame N is source frame N. It carries the colour tags Chrome would apply to the source, since Chrome's guess for an untagged 540-line file differs from its guess for 1080p. Transparent video gets no proxy. While a scrub proxy is being made, the HTML preview polls once per source every two seconds, even when many cuts use it. The footage pipeline treats a pending response as unavailable until its next poll. The cache key is the source's fingerprint, so editing the file makes a new one. Proxies measured 19 MB per minute of 1080p30 footage and 38 MB per minute of 1080p60, and took 7 to 9 s of one core per minute of footage to make, in the shared worker queue at the lowest priority. They are disposable cache entries like the rest.

The preview asks for its videos' proxies on its first paint, which also queues any missing ones. Below its capability, `scrub?path=` answers a proxy's key once it exists and `scrub/<key>` serves that MP4 with byte ranges. A moving seek (`scrub: true`) works like this:

1. The viewer sends one moving seek at a time, the next as soon as the last one has drawn, so a decode is never abandoned before it shows anything.
2. The runtime seeks the composition as usual, so titles, overlays and animation follow the playhead. Videos whose proxy has loaded keep their native seek for later, behind a `currentTime` that reports the requested time, and stay hidden until a proxy covers them.
3. Once the runtime shows every clip active at that time, each visible video's proxy seeks to the video's time and its frame is drawn into that video's hold canvas, marked `data-cutroom-proxy`.
4. After 60 ms without another seek, the deferred native seeks run and the exact frames replace the proxies through the usual hold. Any other command applies deferred seeks first.

If a visible video has no proxy yet, the seek falls back to waiting for the exact frame, which the one-at-a-time rule still makes several times faster than before. On a timeline where every clip is its own element, each new clip must load before the runtime reveals it, which bounds a drag across 2.5 s cuts to about ten pictures a second.

### Editing proxies

Chromium on Linux, and Electron with it, decodes no HEVC, ProRes or DNxHR, so before editing proxies a clip in those codecs played its sound with no picture, and the viewer waited for a frame that never came. OBS records HEVC.

HyperFrames' runtime already knows which videos need a substitute: the preview document carries its codec map, and the runtime asks `<asset>?hf-proxy=h264` for each video whose codec it cannot play (`canPlayType` decides for HEVC and AV1), shows a still while it waits and swaps the source once the request succeeds. Its request carries a priority header, so the sandboxed preview, whose origin is `null`, sends a CORS preflight; the isolated route answers it, allows that header and `range`, and exposes `Retry-After` and the progress header. Cutroom's media service makes the proxy, not HyperFrames' transcoder: that one tags every proxy BT.709 without converting, has no NVENC, keeps its own cache, and makes the whole copy before the clip plays. Requests with a still, a box or the light flag still go to HyperFrames, and so do the videos Cutroom declines: transparent ones, which keep alpha in HyperFrames' VP8 proxy, and HDR ones, which it tone-maps as export does.

An editing proxy is made for an opaque SDR video whose codec Chromium cannot decode in software (anything but H.264, VP8, VP9 and AV1, from the probe). It is H.264 High with every source frame at the source's own timestamps, on the source's own clock, so a Matroska file's millisecond times stay as they are. Export reads the source file. Sources up to 1080 lines keep their size; larger ones play at 1080p, since the viewer is smaller than that, Chromium decodes H.264 in software, and export reads the source. A keyframe every half second and no B-frames bound what a seek or a step decodes. Each frame is tagged with the colours Chrome would draw the source with, by the scrub proxies' rule, through `setparams` in the filter graph, since FFmpeg 8 and later write the frames' own tags over `-color_primaries` and `-color_trc`. Only FFmpeg's own names from ffprobe reach the graph. AAC sound is copied and other sound becomes AAC, for a video that plays its own sound. NVENC encodes it at CQ 25 (about CRF 20) when the one-frame NVENC probe (`nvenc.ts`), run once per server, finds it working, and libx264 at CRF 20 otherwise or when NVENC fails. Decoding uses half the cores, at most six.

A long recording plays long before its proxy is finished, the part under the playhead first. The proxy is made in pieces of about four seconds, each cut midway between two frames, from a plan read off the source's packets alone (`pieces.json`, cached like the probe; 0.3 s for a 17-minute recording). The playlist starts each later segment at its first sample's timestamp, so Chromium can align segments without moving their presentation timestamps. When the pieces omit an audio track that starts before the video, they hold a copy of the opening picture at zero so Chromium preserves the later frames' original times. Once the plan exists, the runtime's request is answered with an HLS playlist that lists every piece from the start, which Chromium and Electron play natively in the same `<video>`: it asks for each piece as the playhead needs it (`<asset>?hf-proxy=h264&cutroom-piece=N`, and `init` for the header the pieces share), and the request waits until that piece is made. Until the plan exists the runtime's request gets 202 with its progress, and the viewer shows "Preparing footage". The piece asked for last is made next: the run in progress stops, unless it makes that piece now or next, and a new one seeks there, then goes on forward and wraps round to the pieces still missing. A proxy the preview waits on takes the encoder from one nobody waits on, after its current piece, and so do the quick jobs, such as another clip's plan.

One FFmpeg process makes a run of pieces as a fragmented MP4 on its standard output, with a keyframe forced at every cut, and the worker files each fragment into the piece its first frame's time falls in, so a piece never depends on counting packets. Times are the source's own from its start (`-copyts -start_at_zero`), as export reads them; AAC pieces carry the source's sound packets from the cut on. When every piece exists, the header and the pieces in order are one fragmented file, which is remuxed with the source's sound, copied or made AAC as before, into the faststart MP4 that later requests and the footage pipeline read. The joined MP4 keeps the opening hold when the pieces have one. The pieces are removed 30 seconds later; a preview still playing them is then answered from the finished file, its piece copied out by FFmpeg. Once it has jumped to a later piece, Chromium's HLS player shows the frame nearest a paused seek, where an MP4 shows the one at or before it; the viewer seeks a quarter of a frame into each frame, where both show it (see [Which frame the viewer shows](#which-frame-the-viewer-shows)). It also gives no frame of a paused video it has just loaded until the video is sought, so the bridge seeks such a video once to where it already is.

The proxy lives in the media cache like the other artifacts: keyed by the source's fingerprint, remade when the file changes, bounded with the rest, and gone with the project. While the runtime waits, the bridge does not wait for that video: a video the codec map marks undecodable that has failed to load, or loaded with no picture, has no frame to hold. Export never reads a proxy: the direct path reads the source and frame capture runs with HyperFrames' render seek, which turns proxies off. `media_list` gives each such video's `proxy` job state, and asking starts it.

### Export dialog

The default editor opens Export from its tool row or Shift+8, matching the owner's Resolve Deliver binding. Both marks select In to Out by default. Out is inclusive in the dialog and exclusive in the engine. Draft, Standard and High are the producer's quality presets. Format, size and frame rate travel in the producer's own request fields (`format`, `resolution` as a HyperFrames size preset, `fps`), which the route checks against the composition: the file name's extension must match the format, `resolution` must be 1080p or 4K in the composition's shape and a whole multiple of it or smaller (`exportSize` in `src/shared/export.ts`, which the dialog uses to offer only those), and a GIF plays at 30 fps at most, as HyperFrames' route enforces. In and Out are composition frames; the route converts them to the export's own frames (`retimeFrames`: the frames whose times fall inside), and the job's range, status and progress count those. HyperFrames draws a larger size by rendering the page at a whole-number device scale factor, so text and vector graphics are sharp at 4K.

The dialog starts the existing `POST /api/projects/:id/render` after pending timeline edits settle, then follows its progress stream. Dismissing it keeps the job running and the tool-row indicator reopens it. `cutroom: { filename, directory, range, gpu }` extends that same request, where `directory` is an absolute existing folder and `range` is null or `{ start, end }` in project frames. The default `.cutroom/renders` folder is created on demand. `GET /api/cutroom/projects/:id/export-defaults?filename=...&directory=...` suggests the first free name in the chosen folder, starting with the project name and then a numeric suffix from 2. Omitting the folder reads the default without creating it. The dialog refreshes this suggestion when its folder changes or a new export starts, and preserves a name the owner typed. A taken file name is still refused before rendering. Every export writes its final output in a hidden `.cutroom-render-*` staging folder beside the destination, which the project watcher ignores. The worker's temporary files, Chromium profile and marked-export plan go into `scratch/render-<server PID>-*` under the [user's export cache](editing.md#export-storage). On Linux, Chromium uses `/proc/self/cwd` to reach that same scratch directory when the full path would exceed its singleton socket limit. Startup sweeps PID-marked scratch left by exited Cutroom servers in the current cache, the previous data directory and OS temp. It leaves HyperFrames' shared temp cache to Studio and the CLI. When the worker's browsers outlive the five-second wait after SIGKILL, the next export retries scratch cleanup.

Extracted frames and prepared animated GIFs share a byte budget under `frames` in the cache. A marked export's plan extracts from a per-export copy of the project, so `frameCache.ts` keys its frames on the project's own file while that file is unchanged since the copy. The worker holds a SQLite file lock while using the cache. Cutroom trims it at startup and after exports, dropping incomplete entries and evicting the least recently used entries until it fits. A sweep skips a locked cache. If another app instance holds the lock, the export uses its own scratch and discards those frames at the end.

Before starting, `exportMemory.ts` caps the capture browsers from the memory free at that moment, the media each capture can see and the frame it writes. For a root composition with fixed media timings, it counts video and audio elements overlapping the range, or the captured runs of a mixed MP4, including transition handles. For those fixed timelines Cutroom asks the producer to defer video extraction and lets the extracted frames supply the video during capture, with the source dimensions supplied as metadata. It keeps source dimensions when extracting frames, so Chromium skips the extra pass that seeks every selected frame to measure visible boxes. FFmpeg mixes audio separately. The capture server leaves browser audio requests empty so they cannot hold up the video frames. The estimate still counts a smaller per-clip cost for the parts of the document beyond the captured frames. Scripted and nested compositions keep the full-timeline estimate. A mixed MP4 checks the full selected range separately in case a source needs the browser after probing. It also allows one browser per 75 frames the browser captures (only the captured runs when the rest are drawn from the sources), because more only add startup time and memory on a short range. When FFmpeg encodes source parts while the browsers capture, it reserves room for those encoders too (0.8 GB each at 1080p, measured at 3.0 GB for four, scaled by frame size). The encoder of the captured frames stays within 1 GB at 1080p but grows with the frame: at 4K it held 2.3 GB for libx264, 2.8 GB for VP9 and 4.0 GB for ProRes 4444, so the plan reserves 0.4 GB per megapixel, 0.55 for ProRes, and at least 1 GB ([measurements](performance.md#formats-sizes-and-rates)). An export that cannot fit one browser and a 2 GB reserve fails at once with the memory it needs, instead of exhausting RAM. The finished file is published with a hard link, which refuses to replace anything that appeared at the destination meanwhile; from then on a cancel is ignored. Cancel waits for the owned worker process group, then removes the staging and temporary folders. Cleanup never touches the destination, and a cleanup that can't be confirmed (for example, a destination folder moved mid-export) is reported with the render's own cause instead of claiming cancellation succeeded.

The media cache stores a source packet index by file revision. Proxy planning can build it, and capture and direct export reuse it across workers. The first export builds it when proxy planning has not. Both export paths read presentation timestamps in FFprobe’s integer clock. The piece resolver selects the source ordinal for each output frame. A loop wraps at the playable video end, even when audio extends farther or the end falls between microseconds. FFmpeg starts at a keyframe chosen by presentation time and verifies the decoded timestamps. A mismatch retries from the start of the file, then fails with the source name and picture ordinal. Capture verifies all indexed local video because an open GOP or an MP4 edit list can change the first decoded picture even at constant speed with matching source and output frame rates. Capture caches the selected source images and uses them again for repeated output frames. A marked export asks for the same ordinals at the original timeline frames.

Frames of plain footage skip the browser when the export is an MP4 of the root composition at its own size and frame rate; any other format, size or rate is captured, since a transparent export has no page colour to draw over and the planner's parity gate covers neither scaling nor retiming. Before a worker starts, `directPlan.ts` reads the document the export renders (track-mix overrides included) and finds, for each run of frames, the clip painted on top: the highest z-index from Cutroom's `cutroom-tracks` layer (a clip's track index), then the latest in the document. Any other z-index in a stylesheet or inline style could reorder clips, so frames showing more than one clip then go to the browser. A run draws from its source when that top clip is a video or image Cutroom placed in a box filling the frame: inline `position:absolute;inset:0;width:100%;height:100%` with any `object-fit`, a video muted or declared silent, at normal speed, with no transition or unknown attribute (an image carries only Cutroom's `clip` class), starting and ending on frame boundaries. The inspector's edits may ride on it: Position (`data-x`/`data-y` over their baselines, which the runtime draws as `translate`), Scale, Rotation, a whole-pixel inset Crop and Opacity, read by the timeline's own `readClipStyle`; any other transform, a crop between pixels or an opacity it cannot read goes to the browser. A placed clip that leaves part of the frame uncovered, shows through, or is a translucent or letterboxed still, draws over the page colour, which is known only when the page or body sets a background and every background that may reach the page, body or composition root is that same opaque colour, and only when no other clip shows in those frames; otherwise the run goes to the browser, unless the clip covers the frame (an antialiased rotated edge must clear it by a pixel). Nothing else in the document may draw over it or move it: no authored script beyond the vendored GSAP library, no script, stylesheet, frame, plugin or event handler anywhere inside the composition (a clip that holds one sends the whole export to capture, even when it lies beneath the video), no linked stylesheet, no untimed element or stray text, no `!important`, and no rule that could reach the page, body, composition root or a clip with a pseudo-element or with anything but colour, font, background, z-index and pinned layout values. Cutroom's generated transition sheet and a region sheet that matches the saved clips are checked separately. The browser draws the animation intervals for dissolves and dips and the active spans of zooms, blurs and highlights. Titles are captured while they are visible over the footage. The remaining runs can still draw from their sources. A modified managed stylesheet goes through the same CSS checks as other authored styles. Every other run goes to frame capture. A document feature that could reach any frame sends the whole export to capture, and the server log says why. Before the worker starts, the server reads each still's header through `projectPath` (`directStill.ts`): a PNG or a baseline or progressive JPEG whose pixels the browser draws as stored, so no colour profile, `cICP`, `cHRM`, `gAMA` or HDR chunk, no Adobe transform, no EXIF rotation and no animation, and whose crop lands on its own pixels. A still that fails goes to the browser and the server log says why. The worker then probes each video source. It must be SDR without alpha, match the composition's aspect ratio, and have square, unrotated pixels and an index of presented pictures. Direct encoding uses the same picture ordinals and SDR colour transform as frame capture. A placed clip is drawn in RGB as the browser composites it: cropped, resampled once to its drawn size, then moved, scaled and rotated about the frame's centre by one bilinear `perspective` warp whose corners carry the exact CSS mapping (pixel centres at half pixels), faded by its opacity and laid over the page colour, before joining the plain parts as tagged BT.709 limited range. A still is drawn once and held for its run. Only numbers and validated colours enter the filter graph; paths reach FFmpeg as `-i` arguments. Parts of at most 300 frames and eight sources encode four at a time through HyperFrames' `buildEncoderArgs`, one closed GOP each, and join without re-encoding. When every frame comes from the sources, NVENC encodes them if the server's one-frame probe (`nvenc.ts`, run once, before the first such export) found it working, at settings that match or beat libx264's quality at each tier ([measurements](performance.md#gpu-encoding)). Otherwise, and when the request chooses a CRF, which is libx264's scale, they use the capture path's libx264 settings. If any NVENC part fails, for example on a frame wider than its 4096 pixels or at the driver's session limit, libx264 encodes every part again, so one file never joins two encoders. A mixed export's source parts join HyperFrames' libx264 parts, so they use libx264 too. The dialog's Encode on the GPU switch and `export_start`'s `gpu: false` keep that export on the CPU without probing; `GET /api/export-gpu` runs the probe once so the dialog offers the switch only where NVENC works. `CUTROOM_EXPORT_GPU=0` keeps every export on the CPU. HyperFrames' `useGpu` request flag no longer sends an export to frame capture; it still chooses capture's own encoder. Only NVIDIA's encoder is used: HyperFrames' VA-API path opens `/dev/dri/renderD128`, which is NVIDIA's node on a hybrid laptop, and NVIDIA's VA-API driver is unreliable. When no frame needs the browser, sound comes from the producer's own audio stage, which a version-checked transform hands to Cutroom, through the range audio path below, so the export carries the samples frame capture would. When some do, the export runs as a marked export of its whole range (a whole-timeline export included): the source parts encode while `renderSpan` plans, its chunk loop captures only the browser's runs, and its stitch joins every part in frame order before the range audio path adds sound. All of a chunk's runs are captured by one `renderChunk` call, so its capture browsers start and load the page once, however many runs there are: the chunk captures a contiguous range of capture indexes, and version-checked transforms of the producer's sequential capture loop and the engine's parallel workers seek capture index `k` to the `k`-th listed frame, while the chunk's video frame extraction and placement use the listed frames. Each run's frames then encode as their own closed-GOP part with the chunk's encoder settings, a few runs at a time. An export drawn wholly from its sources is not refused for browser memory it does not use; if a source turns out to need the browser after all, it fails with that memory refusal rather than starting browsers. `tests/export-direct.test.ts` is the gate for every kind of range the planner accepts: it exports NTSC 29.97 and 23.976 timelines that cut between 25, 29.97 and 59.94 fps sources, untagged BT.601 and tagged BT.709, at half, equal and twice the composition size, with source offsets, plus b-roll over a cut and two title runs captured by one set of browsers, and a timeline with each inspector edit on its own (a punch-in, a smaller turned and moved clip, a cropped and faded one) and three stills (a PNG at the frame's shape, a letterboxed 4:3 JPEG and a half-transparent PNG at 0.8 scale), through both renderers, the direct exports once with libx264 and once with NVENC where the probe finds it. Every output frame must show the same source frame (read from a burned-in frame number, where the edit moved it), differ by under 4/255 on average with under 1.5/255 bias per channel (frame capture's JPEG extraction and screenshots account for about 1.5), and the sound must match. Add a fixture there before the planner accepts a new kind of range.

When browser export extracts SDR footage as JPEG, it uses 4:4:4 for MP4, MOV, WebM and GIF. FFmpeg expands source chroma at its original sample boundaries, then keeps chroma at every pixel in the JPEG instead of subsampling it before compositing. This applies to whole, marked and mixed exports. The version-checked extraction adapter puts these JPEGs under a separate cache key so old 4:2:0 frames are never reused. The final MP4 still uses 4:2:0 for playback compatibility. [Edge measurements and export costs](performance.md#chroma-in-mp4-frame-capture).

Marked exports use the producer's public `renderSpan`, which plans the composition, calls `renderChunk` with the selected absolute `frameRange`, and stitches its MP4 without re-encoding video. `renderSpan` refuses other formats, but its distributed planner and chunk renderer already encode MOV (ProRes 4444) and WebM (VP9 with alpha) with transparent capture, so a version-checked transform lets a span render those too; its one chunk is the span's video, and the final mux adds Opus for WebM and AAC otherwise. GIF, whole or marked, renders a ProRes 4444 MOV in the job's scratch folder and `gif.ts` turns it into a GIF with HyperFrames' palette settings, except that the palette counts every pixel: HyperFrames' own GIF counts only pixels that change, and a title that appears over transparency and stays then comes out black. One local chunk spans the timeline, so only the marked frames are captured and encoded. Planning still prepares source video and evaluates the whole document, but mixes only the audio heard within a second of the range (`rangeAudio.ts`). Those clips stay whole, so source offsets, loops, rate, fades, gain automation and clip effects are computed as in the full mix. The mixer places authored audio on the 48 kHz grid using the clip's exact position through its composition hosts. At 1×, the first output sample reads the source sample at the same whole-sample offset as every other piece of that source line. For local AAC, FFmpeg seeks several packets early and trims by the original timestamps to avoid landing on the next AAC packet. Marked exports subtract the same number of samples from every kept clip and trim the mix at the exact In and Out samples. Every other clip is silence at those samples, so the window holds the full mix's samples. A master or group effect chain and group automation run on the whole timeline's clock, so those mix in full. Owned AAC packets alone can omit samples at either cut boundary, so chunks carry no audio and a final mux copies the encoded video, trims the mix's PCM at sample precision and encodes audio once. The PCM parity target is sample equality. For the 192 kbps AAC fixture the whole and marked encodes must have zero sample lag, with an RMS difference at the encoder's measured floor of about −53.9 dBFS. The delivery true-peak guard sees that window rather than the whole timeline; when the full mix peaks above its ceiling away from the range, a full export can be limited or lowered where the range export is not. Producer scratch lands in the job's scratch folder (patched from the system temp directory in `renderSpan`), so cancellation removes it after reaping the worker process group.

The version-checked render adapter also carries the project's rational frame rate through the native planner's integer-only configuration, publishes native chunk stage counts, and applies `projectPath` before the planner materializes source links. Whole-timeline exports retain `executeRenderJob`. Both paths forward structured producer stages and their frame counts through the existing progress URL. Each job waits for at least one second and five measured frames in the current capture, extraction, or encode stage before estimating that stage's remaining time. The dialog and MCP read that same estimate. Stage changes, retries, and stalled counts discard the estimate. Preparation and final assembly show "Estimating time left". Location stays disabled until its default has loaded.

Completion shows Finished, elapsed time and the published file's byte size as kB or MB. `renders.ts` keeps the renders list: every MP4, MOV, WebM or GIF that is a regular file (not a link) in `.cutroom/renders`, plus each export published elsewhere, which it records in `.cutroom/renders.json` with the file's device, inode, size and modification time. A recorded file whose identity no longer matches is someone else's now and drops out. `GET /api/projects/:id/exports` lists them for the dialog and `export_list`, `GET .../exports/file?path=` serves only a listed file, and `DELETE .../exports` removes only a listed file, refuses agents, and runs in each project's index write queue. Closing a completed dialog resets the tool-row label; its fixed width reserves room for progress and completion without shifting other tools. Hiding an active job preserves its progress and completion until reopened.

The browser shows the saved path and opens the job's existing inline-video route. Electron's isolated preload exposes only Open and Reveal for an MP4, MOV, WebM or GIF, guarded to the main Cutroom frame. `export_start`, `export_status`, and `export_cancel` use that same HTTP render route and the same job objects. Start resolves the dialog's range, quality, and free-name defaults on the server, then forwards with the caller's identity through the existing destination validation. Status reads live stage counts, the shared stage estimator, byte size and failure cause; terminal jobs remain queryable for five minutes after cleanup. Cancel checks the job's project against the native agent's active run and returns the final job snapshot after cleanup. The shared render registry admits only one running export across all projects and clients; another start is refused with the running project, filename and job ID. Job progress travels over the editor's shared project connection, with a read of the one running job (`GET /api/export-jobs`, whichever project is open) when the indicator mounts, so either client can follow and cancel the other's jobs. No second export queue or producer path is introduced.

### DaVinci Resolve export

`format: "resolve"` on the export route writes a folder Resolve opens instead of a render (`src/server/resolve/`). `plan.ts` turns the parsed timeline into FCPXML, `fcpxml.ts` holds exact rational time and escaping, `probe.ts` reads each file's rate, size, timecode and sound, and `export.ts` claims a new folder and writes only inside it. Every frame time is a fraction of seconds, so 29.97 and 59.94 cuts never drift, and a source's timecode, drop-frame included, sets where Resolve numbers its frames from. Rational addition reduces exact integer arithmetic before checking that the serialized time fits a safe integer.

The console importer requires Resolve 21.1.2. Before creating a bin or installing Color LUTs, it checks the version and every media and LUT input. The copied Python script uses a named plan from the same clip placements as the FCPXML. Resolve rejects relative media URLs in FCPXML, so the script resolves packaged paths inside Media, Layers, Sound and LUTs at their current location and imports a temporary document with absolute media URLs. Linked originals use their original paths. Manual FCPXML import can relink a moved package and uses the speed and cut lengths listed in the summary.

- V1 is the primary storyline with gaps. Ordinary V1 transitions use FCPXML. Other video tracks stay as connected clips in separate lanes. The console importer adds Cross Dissolve and Dip To Color Dissolve to their cuts, and adds transitions involving retimed clips after setting their speed.
- Resolve sorts negative lanes from the deepest up, so audio track A1 of N is lane -N. A `<video>` element links the `<audio>` elements inside it, which Resolve places at sequence time rather than the parent's time. It drops keyframes inside a `<video>`, so an animated picture is an `<asset-clip>` of a picture-only asset (keyframes in source time) and its sound a separate clip. Sound with a changing level is a separate clip too. After importing, the console script links clips that had to be separate. Resolve applies static volume and source-time volume keys. Cutroom combines clip volume, group or track gain, fades, volume automation and gain-only effect chains in those keys. Audio transitions with matching fade curves become Fairlight Cross Fade +3 dB for equal power or Cross Fade 0 dB for linear. The summary names cuts that need separate fade curves or lack a source and lists the other effects to rebuild in Fairlight.
- Position and crop are hundredths of the frame's height, y up; rotation is counter-clockwise. Linear and held keyframes keep their keys. CSS eases and region zooms (a perspective `translate`, so the scale is not eased linearly) are keyed on every frame where the motion bends. Resolve rounds key times down in floating point, so keys sit a hundredth of a frame late.
- The console script sets constant speed on the imported linked-to-source items, preserving their timeline range and source in-point. A slow clip shortened by the 100% XML import is extended to its original out-point after retiming. Resolve keeps keys at their full-source offsets through the speed change, so the XML accounts for the new offset. An authored speed ramp still refuses timeline export because the importer can set only one speed per item. The script also adds timeline markers with notes, colours and durations. The marker EDL is available for manual import. On Linux, AAC sound travels as a source-aligned WAV in `Sound/` because Resolve plays AAC silently. The pictures still link the original files.

Clips Resolve can't open as media (titles, scenes, captions, HTML elements and SVG images) render into a transparent ProRes 4444 MOV per video track, covering its first to its last such clip. Each clip gets its own cut of that file on its own track. A graded adjustment, blur or highlight gets a separate MOV for its span with the tracks beneath it. The filenames use their video track, such as `Layers/V2.mov` and `Layers/V2-2.mov`. Each render is an ordinary MOV job, so the editor's export indicator follows it. It reads `layerHtml` (`layers.ts`), which hides other clips and silences every track. The export sets that HTML in an `AsyncLocalStorage` around its own render request, which the render workers' source overrides read. Zoom layers stay visible in every render, so a rendered title zooms with the shot. A failed render removes the export's folder.

The Resolve plan collects grades for the video and still clips it links. The export uses the same 65-point baker as the direct FFmpeg export, with one cube per grade hash in `LUTs/Cutroom Grades/`. A rendered layer already contains its grade. The same console importer applies per-clip LUTs. It imports the FCPXML, finds the planned cuts by video track and frame range, and applies each LUT. On Linux it reads the package’s .cube directly in a per-clip Fusion File LUT, because the default Color LUT folder is read-only and Resolve does not register LUTs from arbitrary files. On macOS and Windows, or with an explicitly registered LUT folder, it applies the LUTs on Color node 01 after checking that new clips use local grades. The summary lists the assignments and the manual steps.

### Variables

Composition variables use HyperFrames' own model end to end. Declarations stay in the source's `data-composition-variables`, parsed with HyperFrames' `isCompositionVariable`; `src/shared/variables.ts` adds the value checks by declared type and the size bounds, and is shared by the routes, the MCP tools and the render route. Preview overrides are not project data: `src/server/projects/variables.ts` keeps them in memory per project and composition, and pushes each change as a `variables` event on the project connection. HyperFrames reads variables once as a document starts and binds text only once, so the viewer requests a new document with HyperFrames' `?variables=` query, which the preview route injects as `window.__hfVariables` with `<` escaped, and promotes it over the last picture like any other reload. Each document remembers the overrides it was requested with. Writing a default or a new declaration rewrites only that attribute's bytes (and, for a binding, the element's `data-var-text` or `style`) inside one history window.

An export's `variables` travel in the producer's own request field, which the capture page sets with `JSON.parse` before scripts run. The named-export route checks them against the exported composition's declarations first, since HyperFrames' route only checks for an object. Any override sends the export to frame capture: the direct planner reads the authored document, which does not know the values.

### Library

`src/server/library/` reads the HyperFrames registry of the release Cutroom pins (`0.9.26`), by the commit its tag names (`LIBRARY_RELEASE` in `registry.ts`), never `main` or the tag itself, so what an editor or agent adds is what the installed runtime plays and a moved tag cannot change it. Update the commit with the packages; a test fails until they match. Only the registry folder at that commit on `raw.githubusercontent.com` and HyperFrames' two folders on `static.heygen.ai` (`hyperframes-oss/`, `hyperframes/templates/`) are reachable. Requests use HTTPS, refuse every redirect, time out after 10 seconds and cap each body. Every manifest is parsed with zod before it is used or cached. An item is left out of the list when a file it would write is absolute, climbs out with `..`, sits at the project root (where tools read `bunfig.toml`, `Makefile` and the like, and HTML becomes a timeline), sits under `node_modules`, or names a hidden or tooling file; and when a file it takes from `static.heygen.ai` (an item's `url`) is anything but a picture, sound or font, so code only ever comes from the pinned commit. Documentation files (`.md`) are dropped first, since they are never copied. Deprecated items, items that need a newer HyperFrames, and items whose HTML, CSS or scripts load anything else from the network ("Needs online scripts": three.js, d3, topojson, Lottie, Google Fonts, about 80 of 448) stay listed with the reason and are refused when added, since neither the preview sandbox nor the renderer can reach it. GSAP and its plugins are the exception: they ship with Cutroom.

The list (one `registry-item.json` per item, and one read of each item's code to find network references) is saved in the data folder as `library/<tag>/catalog.json`; the first read takes about 6 seconds. A complete list is never fetched again, because the commit does not change. An incomplete one is completed on the next read, and serves as is, marked offline, when the registry cannot be reached. An item's files and poster are fetched when first needed and kept beside it, with a record of each file's SHA-256; a record that cannot be read, or a file whose bytes no longer match it, counts as not downloaded and is fetched again.

Adding (`POST /projects/:id/library`, `library_add`) first applies its placement to the current timeline with the shared engine, so a placement the engine refuses (an audio or locked track) is a 422 before anything is downloaded or written. It then downloads, and in one history entry, category `library`, copies each file to its `target` through `projectWritePath`, places a scene clip with the timeline engine and records the item's name, tag, registry source, license and author in `cutroom.json` `library`. An item that names no license records the registry repository's, Apache-2.0, with `licenseInherited`; an item's own licenses, such as a font's OFL text file, are copied with it. A file the project already has with the same bytes is reused, so a second use shares them, and undoing that use leaves them for the first. An edited copy of the item's scene keeps its edits and the new one goes in as `name-2.html`; an edited asset is kept and reported. Library entries can create binary assets, so history treats files a `library` entry created as undoable, like fonts. A block is placed at its own length; a component, which has none, at 3 seconds. Of the 238 components, 170 are whole compositions and go in as they are; the other 68 are fragments meant to be pasted into a host, whose animation is a `tl.` recipe in a "Timeline integration" comment. For those, Cutroom writes `compositions/<name>.html`, a host at the timeline's size that declares the item's variables, includes the fragment and builds its timeline from that recipe. The fragment's own file is not copied: it is not a composition, and HyperFrames' lint would report it as one. Like every library file, the recipe only runs in the preview sandbox and the renderer. Registry items load GSAP and its plugins (CustomEase, MotionPathPlugin) from `cdn.jsdelivr.net`, which the sandboxed preview refuses, so every added HTML file loads them from the project's `assets/vendor/`, which the add fills from Cutroom's pinned GSAP when a project lacks them. A component's host is drawn at the size of the timeline it is first added to; added to a timeline of another size, the item gets a host of that size beside it, as `<name>-2.html`, since a host scaled into another shape would no longer fill the frame. A part marked from an In point is placed at its marked length and slipped by `start` frames, so the clip keeps its place and plays the item from there. The engine writes a clip as it was inserted, so the slip is a second timeline write inside the same history entry; the add checks both against the timeline first. `library_search` and `library_add` count lengths in the timeline's frames. Caches of other HyperFrames releases under `library/` are removed at startup. `library_add` asks for approval even when the owner always allows project edits, because it brings code in from the network.

The source viewer previews an item without adding it. `GET /api/cutroom/library/:name/preview?width&height` builds the item into `library/<tag>/previews/<name>/`: the same files an add would write (`itemProjectFiles`, so the preview and the project never differ), once per server run, and for each size it is opened at, an `index@<width>x<height>.html` that mounts the scene as one clip over black. Only a fragment component's host depends on the size, so it alone is written again per size, as `<name>@<width>x<height>.html` beside the shared files. `bundleToSingleHtml` makes that one document, with HyperFrames' runtime in place of Cutroom's preview bridge. It redirects to `/api/isolated/<key>/<name>/<width>x<height>/`, a random per-session key registered before the project previews, since `/api/isolated/` is the one prefix that answers opaque frames. That prefix serves the runtime and the built folder's files, read-only: nothing outside it, no hidden file, no folder it did not build. Documents get the project previews' policy (`sandbox allow-scripts`, every fetch directive limited to the prefix), and the frame is `sandbox="allow-scripts"`, so an item's code never reaches the editor's page, its storage or the API. The viewer drives the runtime with its own control messages (`hf-parent` play, pause, seek, set-muted) and reads its `state` reports, so the transport, marks and shuttle keys work as they do for footage. Marks for a library item are kept for the session, since it is no project file.

## Animation feedback

Timeline edits never rewrite animation scripts. The shared command route observes actual before/after timelines for each command in a batch and accumulates changes to start minus source in-point at playback rate. Plain elements have no persisted in-point, so `windowClip` carries a temporary source offset through surviving windows while the batch is observed. This distinguishes a head trim from a trim plus ripple displacement without a command-kind list. The offset is stripped before returning the timeline; no warning history or ledger is stored. New IDs use the existing copy/clipboard origins to inspect their source animation too.

`animationFeedback.ts` uses HyperFrames' GSAP parser and complete literal selectors to attribute root animation. Its fallback AST walk handles receiver forms the inspector cannot expand; loose source references apply only to unresolved GSAP target expressions, with selector literals masked to avoid matching class fragments. Sub-composition hosts are always excluded. It does not prove ownership, execute scripts, compare preview reports or compute new tween positions. Animation with no attributable target can remain silent.

The command saves and acknowledges the edit before source inspection. A short-lived callback retains that edit's before/after snapshots. Each page creates a fresh in-memory tab origin token, sends it in the command header and the project SSE URL, and checks it on received feedback. The server delivers the warning only to a matching project stream. The initiating editor shows it after its edit queue settles; observer tabs stay quiet. Commands without a tab origin, including MCP edits, never warn editor tabs. No synchronous warning payload, replay or persisted warning history is involved. Leaving the project dismisses the toast and drops queued feedback from that editor session. The toast uses the existing four-second transient hold. Ask agent uses the existing annotation and Review path.

The MCP bridge requests the same command endpoint as an SSE response: a committed `result` event first, then an `animation-left-behind` event, then stream completion. It returns the first event as the tool result and forwards nonempty feedback as a `notifications/message` warning from `cutroom.animation`, including the project ID, the originating MCP `requestId`, and the committed timeline `revision`. The request ID correlates rapid calls even when their clip warnings are identical. This is a follow-up notification, not a delayed tool result or a polling/job API. A disconnected caller loses its follow-up; no feedback is stored for later delivery. Diagnostic failures are logged after the saved edit and never roll it back.
