# Architecture

Cutroom has one local server and a React workspace. The Electron application is a contained desktop host for that same interface. Startup and shutdown share one lifetime, including a backend that has not finished opening. Linux installation stores immutable app versions under the user data directory and switches a launcher symlink after the copy completes. Project data stays outside those app folders.

The desktop's owned backend also stops when its parent IPC channel closes, including after a forced desktop quit. An existing server that the desktop connects to keeps its independent lifetime.

## Project ownership

Projects remain ordinary HyperFrames folders. The application registry records their paths, while `cutroom.json` stores annotations and original word-timed transcripts. Review status lives in `.cutroom/review.json`, outside project history. `src/shared/review.ts` defines the one transition table that the UI routes, MCP tools, and agent turn lifecycle all pass through, and `src/server/projects/review.ts` runs every review change, plus the note deletes, edits, undo, redo, and restore that could race one, in a single queue per project. One reconcile step there derives status from the live notes and review.json and saves it, before every read and around every history change. Source media is never rewritten by script cuts.

`src/server/projects/store.ts` owns the project registry, serialized Cutroom mutations, and one upstream `ProjectHistory` per folder. The native editor, transcript service, and MCP tools use that same history. Source writes require the exact content version they read. Metadata writes also refuse concurrent replacement. Shutdown rejects new edits and drains admitted mutations before closing history. The notebook reads review items and a transcript revision; full words load when Script is opened.

External changes are watched and sent to the editor through server-sent events. The editor preserves its own file-write receipts, selection, playhead, and conflict handling.

Dot folders such as `.cutroom/` hold app state, including review captures and renders. They are left out of the project file list that Media, Assets, and the code tree read, and their changes do not refresh Media.

`projectWritePath` is the server boundary for user-directed source writes. It allows HyperFrames' authored text types and the editor's `.htm` alias, refuses hidden segments and instruction/tooling configuration, and checks both the requested path and the canonical symlink target. Source saves, timeline/script mutations, and the embedded editor use it for agents and owners, independent of approval. Media management keeps its asset types but cannot target protected files. Embedded renames are refused when the upstream reference writer's project-wide text scan could touch protected content. History validates the files an undo, redo, or restore would change; its fixed app sidecars remain available, without allowing links from them to native settings. App-owned hidden sidecars use `projectStatePath` to refuse redirected write targets; public `cutroom.json` follows the source-write boundary too. This prevents a metadata symlink from redirecting an annotation or review write onto native permissions.

## Editor integration

The public `@hyperframes/studio` application supplies the timeline, canvas editing, preview, inspector, and source editor. Cutroom supplies the surrounding workspace, review tools, agent panel, and original visual theme.

The shell is a fixed, dark-only layout: Media above one work panel on the left, the editor beside them, and a status bar below. Agent, Review, and Script share the work panel. Their components stay mounted while switching tabs so drafts and native sessions survive navigation. Transcript reads run only while Script is visible. Every colour, type size, space, radius, line weight, layer, duration, and easing is a token in `src/client/tokens.css`, a verbatim copy of the design source that `src/client/styles.css` imports once. Its `@custom-media` breakpoints are expanded at build time by Lightning CSS. `styles.css` only arranges the tokens and maps them onto the names the embedded editor reads. Components contain no colour literals. Motion animates only transform and opacity, nothing loops, and reduced motion collapses movement to short fades through the same tokens.

Shell controls read and write `src/client/workspace.ts`, a Cutroom-owned store for editor panel visibility, export state, the open composition's frame rate and size, and the chat panel's agent availability. `CutroomEditor` is the only code that mirrors it onto the upstream dock, so the shell does not depend on the embedded editor's layout internals.

`build/studioPlugin.ts` applies explicit, version-checked changes to the published source. It replaces branded chrome, removes hosted catalog and feedback, disables telemetry, and connects agent handoffs. The source package remains an upstream dependency rather than a copied editor fork.

Keep the HyperFrames packages on the same version. An upgrade must review each source transform, run the editing and preview/export tests, and inspect the workspace in a real browser. A successful build alone is insufficient.

For an upstream upgrade, update all `@hyperframes/*` dependencies and the `hyperframes` CLI together, then update `SUPPORTED_VERSION` in the build plugin. Source transforms fail when an expected upstream section changes. Review that change, adjust the integration, and run `bun run check`, `bun test`, and `bun run test:e2e` before packaging. Public editor improvements then come through the dependency. Features exclusive to the proprietary desktop application require independent implementation.

## Cutroom's own editor

`src/client/edit/` is the editor a project opens in. The embedded HyperFrames editor remains available when New editor is switched off, while the remaining transform and source controls are rebuilt. The default viewer uses the same HyperFrames runtime in an iframe at the composition's size, scaled to fit. `/api/projects/:id/isolated-preview` redirects to a random, server-session capability for that project's preview documents, runtime, GSAP, and assets. That capability cannot serve API routes or another project. The response CSP and iframe sandbox both permit scripts without `allow-same-origin`, so composition code has an opaque origin and cannot access the editor's DOM, storage, or API. Playback, clock updates, dimensions, and seek/paint confirmation cross a message bridge checked against the frame's window. The bridge exposes only preview operations.

Isolated documents have a default-deny CSP. Scripts, styles, media, fonts, and fetches can use only that capability's assets, with inline composition scripts/styles and embedded data or blob media permitted. Forms, child frames, objects, and workers are disabled. Asset responses permit the opaque `null` origin; other API reads reject it. The editor document's `frame-src 'self'` also prevents the isolated frame from navigating to an external site. The server rejects `Sec-Fetch-Site: cross-site` requests outside `/api/isolated/`, including Origin-less navigations to old preview documents that would discard those restrictions. Trusted parent loads are same-origin, and native clients without that header retain their existing access. A `Connection-Allowlist` scoped to the same assets blocks additional Chromium network channels, including WebRTC and speculative connections; DNS prefetch is also disabled. Full network confinement requires a Chromium version that supports that header, as bundled in the desktop app. Other engines still enforce the sandbox, CSP, and API Origin boundary but may allow non-fetch network channels. External scripts, fonts, or media must be downloaded into the project before use.

Both isolated preview assets and the producer's source/compiled asset lookups use `projectPath`, shared from `src/server/projects/path.ts` and re-exported by the project store. Each lookup resolves the canonical root and target before serving the canonical file. File and directory symlinks outside that root receive 403; links within it remain usable. Asset MIME types still follow the requested URL. A missing compiled asset can fall back to the source project, while a rejected link cannot.

**Known limitation:** **New editor** is on by default, so projects open with composition isolation. Switching it off restores the old embedded `@hyperframes/studio` editor, which still uses `/api/projects/:id/preview` on Cutroom's own origin. Its canvas tools require direct preview DOM access. That route is deliberately unchanged while the upstream editor awaits removal. Composition scripts in that editor can still read other projects, write through the API, answer pending agent approval prompts, access the parent UI and storage, and contact external sites. The request guard accepts their same-origin requests, so it does not close those attacks. Keep agent-authored compositions in the new editor; the upstream-removal PR must remove this remaining trusted-content path.

`transport.ts` holds the one playhead: an explicit `stopped | playing | shuttle | scrubbing` state, the frame, and the engine's frame rate, length, and in/out range. React renders only state changes; the timecode, playhead, and agent context subscribe to the store and follow the frame without rendering. At 1x the runtime plays its own media and its clock drives the frame, so sound stays in sync. Stopping parks the runtime exactly on the frame its clock reached. At 23.976 and 29.97 the runtime's end time floors one frame short of the engine's exclusive end, so the runtime stopping by itself on the last frame ends playback or loops it. Shuttle speeds and reverse step the runtime one seek per displayed frame. `timeline.ts` keeps the engine's timeline and undo state for the open composition. Reads, edits, undo, and redo go through one queue, so each starts from the view the previous one left. An edit is applied to the shown view at once with the shared `apply`, so the next key or click already sees it, and stays pending until the server answers. Each read shows the server's timeline with the pending edits applied on top, and a refused edit is taken back while the header toast shows the engine's reason. An edit's commands are built once, from the shown view when the key is pressed, and never rebuilt: a rebuild against newer server state could pick other clips than the ones the user saw. The queue writes an id for every piece the commands cut into their `ids` lists, so the shown piece and the server's piece share an id (the engine never hands out an id twice). A trim, razor or move also snapshots every clip it changes, including linked partners and ripple followers, since a trim or razor cuts at absolute frames and a drag moves a clip to the place the user saw. An overwrite move also snapshots each destination range and the clips occupying it, including empty ranges and linked partners' ranges. An agent moving or inserting a clip into that space changes the snapshot and refuses the edit. A mouse gesture keeps its starting timeline from the press and passes it with its frozen commands on release. The held preview and the queue check the snapshots before replaying the commands, on release, and again before sending them, including after a stale-revision retry. A changed clip refuses the gesture; unrelated edits stay underneath its preview. Export starts through this same queue after earlier edits have settled, and a refused edit is reported instead of rendering the saved version. A stale revision (409) means someone else edited first; the step reads the server, checks those clips again, and sends the same commands. If the engine refuses them after that, the clips changed under the edit, and the header says so; a refusal on the first send keeps the engine's reason. When a step fails, it takes back the queued edits that name a piece the failed edit would have made (the editor chose those ids, so the set is exact), removes those pieces from the selection, and reads the server before the queue moves on.

`src/client/edit/inspector/` reads the selected clip from the same timeline store. Its toggle persists in the workspace store. Below the token's 1304px breakpoint it overlays the stage as a drawer. Arming Draw or Comment closes the drawer so it cannot block the picture. Escape cancels a focused field first, then closes an open drawer from anywhere in the editor and returns focus to the toggle. The next Escape clears selection. Section collapse choices survive selection changes, and Timing starts open. Multiple selection shows a count instead of editing one clip. Start and Duration use the existing move and trim commands; Speed and Source in use `setTiming`, which edits linked media together without changing timeline duration and refuses exhausted media. Each field commits one batch on Enter, blur, or label-drag release; selecting another clip commits before the timeline handles the press. Escape cancels typing. Up/Down steps a frame or percentage point, with Shift stepping ten. Source timing fields appear only on clips with a source. Opacity is a static inline CSS property through `setClip`, parsed and rewritten with Lightning CSS, with exact engine readback and the same source in preview and export. The Auto button removes that inline override. Authored animation can still animate opacity; this is not a keyframe editor. Position, scale, rotation, diamonds, and curves remain deferred until the runtime overlay has preview/render parity.

The inspector's Changes list keeps the most recent 200 clip edits in `.cutroom/review.json`, outside undo history. Each new row stores its history entry id, source signature and claimed note ids. The active history controls visibility: undo hides a row and redo brings back the same row without changing acceptance. The ledger also derives #30's blue clip underline, so undoing and redoing an agent edit removes and restores its mark. Explicit acceptance persists outside history. Accepting a note accepts only its attributed rows; accepting one row never accepts another clip. Existing marks migrate into the same ledger, including their note attribution; older rows without history ids keep their existing visibility and use later owner rows and the live signature for resolution. Changes shows five rows by default, making room for all pending agent work even when older, with Show all for the rest. The timeline and inspector name UI edits once from their commands when the shared edit queue creates the batch.

An unaccepted agent row stays pending across later tracked agent edits to its clip. Its first later active change to that clip outside those agent rows supersedes it. A recorded owner row gives "Edited by you"; an external edit or history restore gives "Source changed". Compare each history entry's before/after clip signatures, so changes to other clips do not count. Ignore undone entries and undo/redo operation entries. A final comparison between the latest tracked signature and the live clip also catches source changes not yet checkpointed. History and signatures derive these states on each read; no resolution is persisted.

App and EditPage share one project event connection per tab. The server forwards the preview watcher's file-change events through that connection too, so three default-editor tabs leave room in the browser's six-connection HTTP/1.1 pool for reads, edits and exports. Agent sessions and active exports each add a stream while open. The preview server's file watcher decides what affects the preview, and its change events start a reload. A reload loads the new document in a second iframe over the live one, at 1% opacity, and seeks it to the latest frame. It promotes the new document only after its runtime has started on a composition root, confirmed the seek within ten seconds, and painted two frames. Anything else leaves the live document in place and reports in the status bar. Viewer and timeline failures are reported separately, and each clears only its own, so a preview that loads fine never hides a timeline the engine refused. Each viewer connection owns an abort signal for its inspection and paint requests; replacing a preview or closing its project cancels them without reporting a failure. Timeline and notebook reads and review-frame captures also abort when their project closes. A saved note keeps its text if its image capture is cancelled, while a capture that fails in the open project reports the renderer's cause. Chromium stops drawing video in a layer that cannot be seen, so a fully transparent or covered frame would show black for one frame when revealed.

`src/client/timeline/` is the timeline. `Timeline` takes the engine's projection, a clock, pins, a selection, and the tool as props; `ProjectTimeline` connects it to the stores above. Pixels per frame is one custom property, `--ppf`, on the timeline's grid, so a zoom step writes one property and one scroll offset. The property is registered as not inherited. The few marks that need it (brackets, markers, pins, the playhead) opt in with `--ppf: inherit`; clips, names, ticks, and timecodes place themselves in percent of a box as wide as the timeline, so a zoom lays them out again without restyling each one. That took the style pass of a zoom step on the 500-clip benchmark from about 790 elements to about 100. One native scroller carries time and tracks, with the ruler, track headers, and corner stuck to its edges, so scrolling runs on the compositor and clip names stick with `position: sticky`. `view.ts` owns zoom and scroll. An animated zoom lays out at the target and plays back from the old placement: clip bodies and ticks stretch on two layers with `scaleX`, while names, labels, and marks only travel, so text never distorts. React renders only when the view leaves the frames and rows it has mounted (the view plus half a view each side) or crosses a ruler step; the playhead is two elements moved by transform from the transport's subscription. Selection rules and view math are pure functions in `selection.ts` and `math.ts`.

Pointer gestures are one state machine in `gesture.ts`: `idle > armed > dragging > commit | cancel`, where a press arms an intent (move, trim, roll, blade, or marquee) chosen from the tool and where on the clip it landed, and 3px of travel starts the drag. The same file holds the snapping math and turns a drag into commands, all as pure functions over the timeline: a drag's preview is the shared engine's `apply` run in the browser, so what is drawn is what the release sends, and a trim that the engine would refuse is walked back to the last frame it takes. `lanes.ts` is the only part that touches the DOM. On each change of frame or track under the pointer it writes a transform to the mounted clips the preview moves, a `scaleX` to those it resizes, and hands the previewed timeline to the canvas; pointer moves between frames write nothing. Bounds for the drag readout are measured before any transform writes to avoid forcing layout across the moved clips. Snapping and modifier changes redraw even a stationary drag, and release recomputes with its own modifiers. The release clears the transforms and makes the edit in the same task, and `motion.ts` slides only clips the drag had not already put in place. Media dragged from the Media panel uses the browser's drag and drop; the row's kind and length wait in `mediaDrag.ts`, because a drag's data cannot be read until the drop.

Filmstrips and waveforms are drawn by `bodies.ts` on one canvas that lies over the clips, under the selection outlines and names. The canvas is two views wide and sits in the scrolled content, so scrolling moves it on the compositor like the clips; it is drawn again when the zoom changes, when the view leaves it, and when media arrives, never by React. `media.ts` reads the media routes below and keeps what it gets in memory: filmstrip metadata and sprite sheets, single frames (decoded pixels are capped by bytes, 192 MB of sheets and 32 MB of frames, least recently drawn closed first and never one the current view draws), and waveform ranges in chunks of 8,192 buckets per level. A waveform is drawn from the coarsest level whose buckets are no longer than a device pixel; while that level loads, a neighbouring level already in memory is drawn. Only the ranges under the canvas are fetched. When a filmstrip tile covers less than the sprite's two seconds, its frame time is the clip's media start plus a whole number of steps of 1 s, 0.5 s, and so on down, so the first tile is the clip's first frame and neighbouring zooms share frames. Frames are asked for only after the view has rested 150 ms, only for tiles on screen, four at a time. Any zoom or scroll empties the waiting list at once, and media that arrives while the view rests asks again. A `src` resolves to a project file through `localMediaPath` in `src/shared/media.ts`, the same function the server uses.

`src/client/keymap.ts` is the single key table, keyed by Resolve action id. It drives the handlers, button tooltips, and `docs/keyboard.md`; a test keeps the docs in step.

Draft notes, pending saves, and pending frame captures live in `edit/noteStore.ts`, keyed by project outside the editor's lifetime. Chat waits up to three seconds for its project's captures, then reads the notebook again for attachment paths so a completed capture does not depend on a React refresh. A failed or timed-out capture does not block sending; capture-refresh errors are shown only while their project is open. A save failure returns the original draft, including every stroke, even if another project is open. The client creates a UUID before saving and sends it to the annotation endpoint, which validates it and rejects duplicates. Pending and durable notes reconcile by that id before numbering. `noteStore.ts` queues annotation posts per project in commit order, without waiting for frame captures, so notes appear as soon as they are committed and capture completion cannot reorder their numbers. A failed post still lets the next queued note save. After a post succeeds, the client captures its frame and attaches the image through the review service. These late attachments live in `.cutroom/review.json`, outside content history: they add no undo step and never change a sent request or its status. Review reads, including MCP `review_list`, join these images onto the note; existing images in `cutroom.json` remain readable. Saved notes show at their exact frame when parked; during playback a crossed note stays for at least one second and fades over 200ms. Accepted and withdrawn notes leave the picture.

The note overlay lives in the trusted viewer stage outside the sandboxed iframe. It fetches the server thumbnail, whose renderer loads the isolated preview, and composites the note's strokes onto that PNG in the workspace before storing the attachment.

## Timeline engine

`move` defaults to overwrite, clearing only its destination spans with the same trim/split operation as overwrite inserts. All selected clips and their linked partners move before those spans are cleared, so the selection cannot erase itself. New pieces use the command's `ids` lists, including in the optimistic editor queue. `mode: "place"` keeps overlap refusal. The drag preview draws the engine result, including shortened clips, new tail pieces, and fully covered clips hidden until the drag ends.

`src/shared/timeline/` defines the timeline projection and command union as zod schemas, and a pure `apply(timeline, command)` that the browser and server share. Frames are integers at the root's `data-fps` (30 when absent). A value HyperFrames ignores, including decimals such as `29.97`, is refused instead of being read as 30, and NTSC spellings name their exact rate (`30000/1001`); HTML and `cutroom.json` keep seconds rounded to six decimals.

Timing model: a clip spans the frames the runtime shows. Source offsets (`data-media-start`) are canonical at the microsecond: parsed once, and command inputs are rounded in the schema. Commands compute source times exactly from frame counts (frame rate as a fraction, times playback rate) and round once, when the timeline is written. Within one batch, 300 one-frame trims land on the same microsecond as one 300-frame trim. Separate requests each store six decimals, so repeated single edits can drift by up to half a microsecond per write; 300 one-frame trims sent one request at a time measured about 100 µs (10.999900 s against 11 s at 30 fps). The projected offset is the source time at the first shown frame; a start the editor wrote, within a microsecond of a frame, never shifts it, so a rounded NTSC start reads back unchanged.

`src/server/timeline/` parses composition HTML and the `cutroom.json` timeline settings into that projection. parse5 builds the HTML spec tree, including implied end tags and foster parenting, and records byte offsets. One scope rule decides what a file renders, and the projection, the readback after an edit, and media discovery all use it: the entry `index.html` renders its live tree, where `<template>` content is inert as in the browser, and any other file is a sub-composition whose content is its first live `<template>` when it has one, as HyperFrames loads it. The offsets let applied commands become attribute edits, element removals, and inserted copies. An element is removed or copied only when it owns its source bytes: every start tag, end tag, and text in them belongs to its subtree, and its whole subtree lies in them. Otherwise the edit is refused, for example when a `<div>` written inside a `<table>` is moved out of it, text inside a table merges into the text before it, or a `</b>` inside the clip closes a bold begun outside it. Media without an authored duration is measured once per file version with ffprobe, using the media worker's shared protocol and container allow-list to reject playlists and indirect inputs before they can open other files or network URLs. The result must parse back to exactly the applied timeline before it is written. `POST /api/cutroom/projects/:id/commands` applies a batch in one store mutation and history window; the revision covers the HTML and its settings. The MCP `timeline_*` tools call the same routes. A clip id is spent for good: before a batch or a script cut writes, every id in the timeline before and after it is added to `.cutroom/ids.json`, which lives outside undo history, and `apply` refuses a named id in that list and generates others around it. Undo and redo swap whole files and never consult it, so a clip they bring back keeps its own id.

Track metadata in `cutroom.json` includes name, kind, lock, auto-select, enable, mute, and solo. `SetTrack` creates an empty track on a new index. Media drops above the top video row or below the last audio row batch that command with the insert, so undo removes the clip and its new track together. The lanes reserve a full track-height drop zone at each edge so a new-track preview stays inside its target. Right-clicking the header area offers Add video track and Add audio track, which append to their respective stacks. This follows the header-context-menu entry point in the [Resolve 21.1 manual](https://documents.blackmagicdesign.com/UserManuals/DaVinci_Resolve_21.1_Reference_Manual.pdf), chapter 41.

UI and MCP video inserts split sound into a muted video and a linked `<audio>` with matching source offset and duration by default. `Insert.linkedAudio` can name the partner's id; callers do not need to request separation. The engine chooses the first unlocked audio track with room for the entire interval after any insert ripple, provided that track is empty or contains only linked picture sound. A gap on a music or voice track does not make it a picture-sound destination. Otherwise it creates a track. Silent video and `clip.muted=true` stay video-only. The editor names both ids before the optimistic edit, and the server preserves them so following edits can name either partner.

Picture visibility and sound suppression are separate. Disabled tracks hide picture; mute suppresses every sound on its track, including embedded video audio in hand-written compositions. Audio solo excludes sound on every non-solo track, including video tracks, without hiding their picture. MCP can mute a video track's embedded sound through `SetTrack.muted`; solo selects audio tracks. Multiple solos add together, and mute wins over solo.

Hidden clips write `data-hidden`; `data-cutroom-track-hidden` distinguishes a track override from a clip's own disable flag. Suppressed embedded video sound also writes `muted`, which the producer's browser discovery honors without hiding the picture. The version-checked producer adapter makes browser media discovery skip `[data-hidden]` elements and their descendants, just as static parsing does. This also protects saved hidden audio without requiring a new edit. `data-cutroom-muted` marks that override so readback retains the video's original `hasAudio`, and unmuting restores authored mute and gain. Splits, moves and undo preserve these distinctions. Solo persists in `cutroom.json` and is undoable so preview and export use the same mix, as recorded in the project plan. These controls use the same commands and readback through MCP. The viewer's master mute remains local monitoring state and does not change export. Export shows a one-line notice identifying soloed or muted tracks. Preview readback and render preparation reapply the saved mix to outside HTML changes in memory, including each bundled scene instance. Render workers receive those effective sources before static parsing and browser discovery. This adds no source writes or undo entries.

Clip mixing uses HyperFrames' native attributes. `SetClip.volume` is linear gain, with unity at 1 and the core `MAX_AUDIO_GAIN` ceiling at +12 dB. `SetClip.fadeIn` and `fadeOut` are authored integer timeline frames, projected from `data-fade-in` and `data-fade-out` seconds. Writes retain microsecond precision, so even a one-frame NTSC fade reads back exactly. Reads and fade edits preserve authored lengths, including lengths beyond the clip. Ordinary edge trims, including rolls and the edited edge of Q/W, never rewrite native fades. Preview, render, display and handles use core `clampFadesToDuration`, which scales both fades proportionally when their sum exceeds the duration. Splits, overwrite and ripple cuts instead preserve the surviving source envelope without adding fades at internal cuts. A truncated or proportionally scaled ramp becomes HyperFrames native `data-automation` volume breakpoints, retaining its original endpoint beyond the piece so an extension cannot hold a mid-fade level. Existing volume automation is multiplied into those breakpoints, and other lanes retain their targets. On a head cut or trim, clip-local automation moves with the surviving source. Native automation cannot retain points before the new start, so head trim and extension of a baked ramp can lose its earlier envelope; source-anchored envelopes are deferred to keyframes. FX attributes are left intact; clip gain and fades multiply the runtime's resolved level. A GSAP tween on volume retains HyperFrames' absolute-volume semantics and can override static clip gain.

Gain and fade handles use the existing gesture state machine, shared engine preview, frozen clip snapshots, and single command batch on release. The gain drag moves in 0.1 dB increments, with a 0.5 dB change per vertical pixel, from silence to +12 dB. Fade drags start at the effective handle rounded to a whole frame and set that edge's authored length between zero and the clip's duration; the other authored fade stays unchanged. The clip's SVG draws its native volume automation and fades at the gain line's level. A transparent stroke on that same path is the gain hit target and follows the envelope during the preview. No server writes occur until release.

The isolated preview permits autoplay and opts media into CORS before loading it, so HyperFrames can route it through Web Audio even in an opaque origin. The bridge starts the runtime's `__hf.audioMeter` tap only for the promoted preview and sends its master stereo peaks once per animation frame during playback. The parent validates each sample and writes directly to the 36px meter column without React renders. Stopping sends zero levels and disposes the tap; no meter clock runs while idle. Peak marks hold for 1.5 seconds, then fall during playback. Meter colours come from the existing tokens.

Higher video tracks composite above lower ones, as in Resolve. HyperFrames reads track and CSS `z-index` independently. Inserting a visual clip, splitting one, or changing its track, start, or duration establishes track-derived `z-index` defaults in the `cutroom-tracks` cascade layer. Once a managed stylesheet exists, every edit maintains it. Label and gain edits alone do not create one, and audio elements are excluded. Visual track attributes are normalized to canonical `data-track-index` values when defaults are written, including legacy `data-layer` and values such as `"02"`.

The entry document's managed stylesheet goes first in `<head>`, before authored cascade layers such as Tailwind's utilities. A scene's stylesheet goes first inside its loaded template, or in its head when it has no template. HyperFrames extracts scene styles before mounting their content, scopes them to each runtime scene instance, and hoists them into the entry head. A scene edit also declares the shared layer first in the entry head, in the same history transaction, so entry-page utilities retain their priority even when only a scene is edited. Styles stay outside clip children, preserving positional selectors. Each composition's defaults match only its own timed clips and stop at nested composition or clip content. Inline styles, unlayered CSS, and later authored layers override the defaults. Managed blocks are found across the source document, relocated rather than duplicated, and excluded from authored id-reference scans.

## Native agents

Codex runs through its app-server protocol. Claude Code runs through the Agent SDK with the installed executable and native Claude Code prompt. The adapters preserve the user's home, project directory, configuration, skill discovery, MCP connections, and recorded native session IDs.

Cutroom tools declare `readOnlyHint` at registration. Both native adapters derive permissions from that registry. Read tools, including the isolated `timeline_view` capture, run without approval unless native user or project settings ask. Mutating tools ask until the owner chooses **Always allow Cutroom edits** on an approval row. That choice is saved per project in the app's `agents.json`, outside composition files. The Agent panel shows the grant and a Revoke control; revoking also stops active native sessions so their permission entries cannot keep running. Only mutating tools with a required project id are covered. Project creation and import have no existing target, always prompt, and never enter a native session's edit allow list.

Claude receives exact `allowedTools` entries and adds exact edit rules to its session through `updatedPermissions` when the owner grants access during a turn. Native ask and deny rules still win. Codex reads effective project configuration with `config/read`, sets the Cutroom server default to `prompt`, and sets registered tools' per-tool approval modes. Explicit native `prompt` entries win, including restrictive ask entries in untrusted project layers. During an already-running turn, only privileged `mcp_tool_call` approval elicitations for registered Cutroom edits can be answered from the saved choice. Server forms, shell, unknown tools, and other MCP servers keep their native permission flow. New and resumed sessions receive the current project choice. Approval rows derive their action and target from the same registered MCP argument schemas used for execution, including defaults and discarded extra properties. The exact tool identity is always visible next to the action; both wrap instead of truncating. See the [Claude SDK permission rules](https://code.claude.com/docs/en/agent-sdk/permissions) and [Codex configuration reference](https://developers.openai.com/codex/config-reference).

Review ordering is saved in `.cutroom/review.json`. The owner can move unfinished notes up or down in Review; outside MCP clients can use `review_reorder` on the owner's behalf, while Cutroom's own agent is refused. Withdrawal uses the existing state transition and preserves its reason.

Every project mutation route checks a native token's active run and project before parsing input or entering a mutation, including non-HTML writes and metadata repair. The editor and attachment routes use the same guard; job cancellation checks the job's project. Agent controls and owner review routes reject agent headers. Collection creation/import validate an active token without granting access to the resulting project. Owner UI requests and external MCP clients retain their existing authority.

Timeline commands, script cuts, and HTML source writes compare stable clip ids and authored content around the same mutation, under the review queue. Pending agent clip signatures and their claimed note ids live in `review.json`, outside undo history. Edits accept `noteId` for the claimed note they address. A single claim is automatic; with several claims the caller must name one before writing. Accepting a note therefore clears only the clips attributed to that note. The timeline draws a `--agent` blue underline above its media canvas. Accepting the associated note clears its marks; **Accept agent changes** also accepts marks from direct chat edits with no note. A human edit clears the changed clips, and later reads discard marks whose source no longer matches. Track locks, selection, markers, and range changes do not accept a clip's content.

Some read tools persist derived state, including `review.json` reconciliation by `review_list` and history initialization by `history_list`, just as opening the project or Review tab does.

The application persists conversation presentation separately from the provider's session. Streaming deltas do not rewrite history on every token. Approvals and questions are explicit pending requests; stale answers are refused. Model changes retain the native session and conversation. A single operation owns each pending or running turn and model change. Stop also cancels preparation, and callbacks from replaced runtimes cannot alter a newer run.

## Rendering and transcription

Preview and export use the public HyperFrames compiler and renderer. Export runs in an isolated Node worker because the producer's Node HTTP adapter modifies globals that Bun's server also uses. Keep `renderWorker.ts` beside `jobs.ts` when packaging. Cancellation waits for the owned process group and partial-output cleanup before shutdown completes.

Thumbnails and MCP `timeline_view` use the same capability-scoped, opaque documents as the new viewer. Their Chromium request guard permits only GET/HEAD to that capability, plus embedded data/blob resources. Export's producer already owns a separate project-only HTTP server. `renderIsolation.ts` applies version-checked Node loading transforms to put the same sandbox/CSP on every document that server serves and install the request guard before its capture and static-verification pages navigate. A mismatched package version or transform refuses export. The producer adapter also prevents browser discovery from reintroducing hidden media into the render mix. These transforms, as well as `build/studioPlugin.ts`, must be reviewed on a HyperFrames upgrade. No dependency files are changed on disk.

Frame-capture Chromium is reused by thumbnails, note images, and `timeline_view`. `captureBrowserWorker.ts` owns that browser through a DevTools pipe. Chromium exits when that pipe closes, including when SIGKILL kills the owner alone or the server's whole process group. Chromium also exposes an ephemeral loopback WebSocket endpoint, published through `DevToolsActivePort`, so the server can keep using Puppeteer directly without relaying capture traffic through the owner.

The server closes the owner's IPC channel on renderer disposal. The OS also closes that channel whenever the server process ends, so a surviving owner closes Chromium, waits for it, and removes the profile. The owner handles SIGINT, SIGTERM, and SIGHUP too. A five-second fallback still kills Chromium's process group if graceful close stalls. On Windows it kills only the root process. A stopped browser cannot process pipe closure, so Puppeteer's detached browser group remains necessary for that fallback.

Capture profiles are named `cutroom-capture-<owner PID>-<random suffix>` in the temporary directory. A new owner sweeps only matching directories whose PID no longer exists. Live owners, reused PIDs, unmarked directories, and symlinks are preserved. The PID is part of directory creation, so a killed owner cannot leave a new profile without an owner marker. SIGKILL can leave the profile until the next capture owner starts; graceful shutdown removes it immediately. Playwright sends SIGTERM and waits for cleanup before escalating. Keep the worker and `captureProfiles.ts` beside `captureBrowser.ts` when packaging.

Local transcription uses an already installed Whisper runtime and complete model. It runs outside the project in a temporary working folder, then imports normalized words through a history transaction. Job cancellation and shutdown await cleanup before closing project histories.

## External agents

Both MCP transports forward to the running server. They do not open a second project store or write files independently. The server binds to loopback and rejects foreign browser origins and rebinding hostnames. This endpoint is intended for agents on the same machine, not public network exposure.

Every mutating HTTP request, including upstream editor and `/mcp` routes, requires an exact allowed Cutroom `Origin`. Missing, opaque, foreign, or wrong-port origins receive 403 before route dispatch. The stdio MCP bridge supplies the selected server origin; native HTTP clients must do the same. Development additionally permits the two explicit Vite origins. This protects isolated previews and foreign browser pages while preserving the embedded editor's own canvas mutations. It is not authentication against native processes on the same machine, which can set HTTP headers.

## Background jobs and timeline media cache

Render, transcription, waveform, filmstrip, and precise-frame jobs use `src/shared/jobs.ts`. Jobs move from `queued` to `running`, then `done` or `failed`. Cancellation enters `cancelling`, then `cancelled` only after cleanup succeeds. Cleanup failure takes precedence over cancellation and enters `failed`. Render and media cleanup errors also propagate through their cancel/shutdown calls. Running progress uses 0 to 1. The render adapter preserves `rendering` / `complete` and 0 to 100 progress; transcription preserves `running` / `complete` and 0 to 1. Transcription MCP status forwards the same HTTP response; there is no render-status MCP tool.

The migration also fixes main's HTTP render-cancel bug. Upstream assigns `status = "cancelled"` before invoking `cancel()`. Main's old cancel guard then returned without stopping the worker. The adapter now translates that assignment into the cancellation transition, keeps the HTTP status `rendering` during cleanup, and lets the route await cancellation. Cleanup errors return a failure instead of claiming the partial export was removed.

### Media endpoints

- `GET /api/cutroom/projects/:id/media/probe?path=...` exposes the existing cached media probe. A ready response contains audio `channels` and video dimensions, frame rate, and duration when present. The Media panel uses channels to decide whether a video drop needs linked audio. It follows the same 202/job lifecycle as the preview assets.

- `GET /api/cutroom/projects/:id/media/peaks?path=...` returns the complete binary cache file. Add `level`, `start`, and `end` to stream just one mip level and time range. Times are seconds; end is exclusive. Buckets intersecting the requested range are included. Defaults are level 0, start 0, end of media. A nonexistent level or reversed range returns 400.
- `GET /api/cutroom/projects/:id/media/filmstrip?path=...` returns version 2 metadata with `interval`, `tileWidth`, `tileHeight`, `count`, `key`, and `sheets`. Each sheet has `index`, `start`, `count`, `columns`, `rows`, and `spriteUrl`. Tile indexes run left to right, then top to bottom, within a sheet. The final row may contain black unused cells.
- `GET /api/cutroom/projects/:id/media/frame?path=...&time=...` returns a small JPEG at the requested source frame. Time is quantized down to a frame using the probed native frame rate. The cache key includes that frame index, so requests for the same frame share work.

These endpoints return `202 {key, job}` with `Retry-After: 1` and `Cache-Control: no-store` while preparing. Poll the same URL. Shared source probing is itself a queued job; its key may be replaced by the asset job's key on a subsequent poll. Failed jobs return `422 {key, job}` with an error, remain visible for thirty seconds, then permit retry on the next request. Missing audio/video streams are rejected with 422 from the cached probe information, before an asset worker starts. Editing the source changes its fingerprint and permits an immediate retry. Missing FFmpeg or ffprobe returns 503. Source-path responses use private revalidation ETags; matching `If-None-Match` returns 304. Peak ETags include the selected level and bucket range. Key-addressed sheet URLs are private and immutable, with a sheet-specific ETag. No media MCP tools are registered.

### Scheduling and storage

The service runs at most two media worker processes. Frame requests have the highest priority and run newest-first within that priority. Requesting an already queued frame again moves its shared job to the front. Probing and peaks follow, with FIFO ordering at their priority. Only one filmstrip job may run at a time, reserving capacity for interactive work. Each worker runs one FFmpeg or ffprobe process at a time. Decoding, min/max aggregation, and sprite assembly run outside the server process. On POSIX, the server owns each worker's process group and kills its FFmpeg descendants even if the worker crashes. Shutdown cancels queued jobs, terminates active groups, awaits all cleanup, and propagates cleanup errors before project histories close.

The cache lives in `<project>/.cutroom/cache/<key>/`. Its SHA-256 key includes the recipe version, output kind, canonical source path, size, nanosecond mtime/ctime, inode, and device. Frame keys also include the source-frame index. This fingerprint avoids hashing an entire large video before every warm response. Inode/device identify replacements whose timestamps were preserved, including copies from filesystems where ctime mirrors mtime. Identical copies may use separate cache entries. The source fingerprint is checked again before atomic publication. Complete directories appear by rename; temporary frame files are cleaned before publication. Disk-cache eviction is deferred; entries are disposable.

Paths and cache locations use the project boundary check, including symlinks. FFmpeg accepts local media demuxers, including MXF, Wave64, and CAF, while excluding playlists and network protocols. Frame patterns and sprite paths are relative to the worker's task directory, so a percent sign in the project path cannot become a pattern directive.

### Waveform format

The first audio stream decodes to interleaved signed int16 PCM at 48 kHz without downmixing. Each bucket takes extrema across every channel, preserving out-of-phase stereo and a one-sided microphone at full amplitude. Base buckets span 96 sample frames, or 2 ms. Mips reduce groups of four pairs until the first level covering the four-second target. Widths are 2, 8, 32, 128, 512, 2048, and 8192 ms. The final partial bucket and partial mip groups retain their samples. These constants live in `src/shared/media.ts`.

CRPK version 2 is little-endian. The complete file has a 144-byte header/directory followed by all seven level payloads. A ranged response has a 48-byte header/directory and only its selected pairs; it remains a valid CRPK file.

| Byte offset | Field                                                                                                               |
| ----------- | ------------------------------------------------------------------------------------------------------------------- |
| 0           | ASCII `CRPK`                                                                                                        |
| 4           | uint32 version, currently 2                                                                                         |
| 8           | uint32 number of levels in this response                                                                            |
| 12          | uint32 decoded sample rate, currently 48000                                                                         |
| 16          | float64 total decoded sample-frame count, including all channels once per frame                                     |
| 24          | uint32 base bucket width in sample frames, currently 96                                                             |
| 28          | uint32 first bucket index in the selected level, zero for a full file                                               |
| 32          | One 16-byte directory entry per returned level: uint32 sample frames per pair, pair count, byte offset, byte length |

Each payload pair is an int16 minimum followed by an int16 maximum. Normalize amplitudes by 32768. Duration is total sample frames divided by sample rate. For ranged responses, pair time is `(firstBucket + pairIndex) * sampleFramesPerPair / sampleRate`. The server reads the directory and streams only the requested payload bytes. A two-hour overview at the coarsest level is 879 pairs plus header, or 3564 bytes, instead of the roughly 19 MB complete file.

### Filmstrips and precise frames

Overview frames use keyframe-only decoding at the fixed two-second interval. A gap beyond the interval plus one source frame triggers per-tile seeking. Otherwise the worker keeps the keyframe tiles and seeks only missing tail slots. Seeks use source-frame boundaries so the last frame is available when the final tile slot lies within its duration. A long audio stream cannot add phantom video tiles; seeking stops when no video frame exists. Frames retain the source display aspect ratio, including pixel aspect and rotation, at a fixed height of 90. Width rounds to an even pixel count for JPEG. No portrait letterboxing is applied.

Sprites contain at most 100 tiles and ten columns. This bounds sheet memory and dimensions and removes the former two-hour single-sheet limit. Precise on-demand frames use accurate seeking rather than keyframe-only decoding, making shots within an overview interval reachable. Interval, height, sheet limits, and JPEG quality share the same constants used by the metadata schema and FFmpeg filters.

Run `bun run bench:media` to generate a nominal 60-second 1080p testsrc2/sine sample at 30000/1001 fps with a 60-frame GOP and a brief blue shot inside overview tile 0. The benchmark exercises the three endpoints cold and for 30 warm reads, checks the tile count against the probed NTSC duration, records per-mip bytes, range bytes, health latency and logical/allocated cache sizes, and captures a dark 1720-pixel-wide image. It also creates a lossless impulse fixture and draws a 32-pixel-per-frame crop at 60 fps beside the on-demand frame. The script prints its temporary output directory and retains all generated evidence.

### Export dialog

The default editor opens Export from its tool row or Shift+8, matching the owner's Resolve Deliver binding. Both marks select In to Out by default. Out is inclusive in the dialog and exclusive in the engine. Size and frame rate come from the project; Draft, Standard and High are the producer's quality presets.

The dialog starts the existing `POST /api/projects/:id/render` after pending timeline edits settle, then follows its progress stream. Dismissing it keeps the job running and the tool-row indicator reopens it. `cutroom: { filename, directory, range }` extends that same request, where `directory` is an absolute existing folder and `range` is null or `{ start, end }` in project frames. The default `.cutroom/renders` folder is created on demand. A taken file name is refused before rendering. Every export writes into a hidden `.cutroom-render-*` staging folder beside the destination, which the project watcher ignores, and the worker's temporary files live in a separate folder in the system temp directory. The finished file is published with a hard link, which refuses to replace anything that appeared at the destination meanwhile; from then on a cancel is ignored. Cancel waits for the owned worker process group, then removes the staging and temporary folders. Cleanup never touches the destination, and a cleanup that can't be confirmed (for example, a destination folder moved mid-export) is reported with the render's own cause instead of claiming cancellation succeeded.

Marked exports use the producer's public `renderSpan`, which plans the composition, calls `renderChunk` with the selected absolute `frameRange`, and stitches its MP4 without re-encoding video. One local chunk spans the timeline, so only the marked frames are captured and encoded. Planning still prepares source video and the complete audio mix. Owned AAC packets alone can omit samples at either cut boundary, so a final mux copies the encoded video and trims the complete mix at sample precision, encoding only audio. Producer scratch lands in the job's staging and temporary folders, so cancellation removes it after reaping the worker process group.

The version-checked render adapter also carries the project's rational frame rate through the native planner's integer-only configuration, publishes native chunk stage counts, and applies `projectPath` before the planner materializes source links. Whole-timeline exports retain `executeRenderJob`. Both paths forward structured producer stages and their frame counts through the existing progress URL. The dialog waits for at least one second and five measured frames in the current capture, extraction, or encode stage before estimating that stage's remaining time. Stage changes, retries, and stalled counts discard the estimate. Preparation and final assembly show "Estimating time left". Location stays disabled until its default has loaded.

The browser shows the saved path and opens the job's existing inline-video route. Electron's isolated preload exposes only Open and Reveal for an MP4, guarded to the main Cutroom frame. No export MCP tool exists; agents that export use the local HTTP render endpoint and the same options, with the existing Origin and owner-control rules. No second export queue or producer path is introduced.
